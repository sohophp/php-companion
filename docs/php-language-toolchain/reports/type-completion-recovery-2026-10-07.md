# D158：连续文件更新期间的类型补全恢复

## 问题与修改

原服务器只重试一次候选搜索。定向编辑器复现中，连续两次索引失效后返回了空的 incomplete 列表；文档 version 2 未变、请求未取消，停止输入后原 10 秒窗口内没有弹窗。正常对照约 452 ms 显示候选。这证明一个实际缺口，但尚不能确定 D152 原完整 C1 失败也由同一机制导致。

现在在同一个请求中恢复连续失效的搜索：重试前让出事件循环，保留文档身份、版本及取消检查，设置 1000 ms 的额外恢复窗口。超过窗口仍失效时返回空的 incomplete 列表，后续新请求仍可查询；因此不承诺持续无限文件更新时也能自动显示候选。普通查询不增加等待。此恢复窗口不是放宽原 150 ms 热查询预算；底层异步操作仍需完成或响应取消，不把它描述为整个请求的硬超时。

客户端增加测试环境开关下的自动补全结果日志，记录版本、取消、缓冲区摘要和实际返回项；无新增用户配置，默认不记录源码或候选日志。语义事实和缓存 schema 不变。

## 失败记录与范围

三次诊断运行原始结果均保留：第一次缺少 real-vendor 必需标志，未执行编辑器观察；第二次原产品复现空列表，但第一次项目代次变化不能归因到指定的无关文件；第三次修复产品返回了候选，探针却因其它待处理文件事件提前释放而未到达第二个暂停点，不能算弹窗验收。最终探针改为等待目标／消费者以及每个指定变更文件的真实 `index:delta complete` 日志，再输入或释放暂停，不靠项目计数猜测文件完成。
