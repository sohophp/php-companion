# C1 首次 References 候选遍历

日期：2026-09-25。独立 Composer 项目包含已安装的真实 vendor 和约 9,100 个无关 PHP 文件；VS Code 1.139.0 Linux x64 隔离 Core 源码宿主。未修改业务项目，也未打包 VSIX。

首次点击 `ResponseInterface::getStatusCode()` 的 References 返回调用与声明两个正确位置，但单次命令约 1.1 秒。原测试只记录命令总等待，现增加仅在测试模式收集的服务器总耗时、候选预筛和 `indexComposerSources` 遍历耗时。分段复测得到总等待 1,144 ms、服务器 1,005 ms、预筛 35 ms、遍历 940 ms；该次没有候选 epoch 重试。因此先优化候选遍历的让出频率，而不修改 PHP 语义或预筛范围。

候选扫描仍以 128 个并发读取，并保留每个文件的取消检查；仅将这一路径的事件循环让出间隔从每 10 个文件改为每 100 个文件。相同夹具的两次后续冷查询均返回相同两个位置，总等待分别为 1,051/901 ms，遍历分别为 767/736 ms。样本量小且每次是新宿主进程，只说明这组本机对照的改善，不能当作稳定 P95 或跨平台预算。

定向真实 stdio 的三项回归通过：查询中取消后不返回旧结果、新增未打开文件进入 References，以及交替方法查询继续复用各自证据。另一次冷 Implementation 返回正确 Guzzle Response 落点，命令等待 1,366 ms；它含不同的候选范围，没有与本轮 References 数字直接比较。Language Server 构建、扩展宿主 TypeScript、改动文件 ESLint 和差异检查通过。

当前冷查询剩余等待主要仍在带完整性证据的候选遍历；不能跳过文件变化核对来换取更短等待。下一轮应在更大 Composer 项目复核取消响应和冷/热分布，再针对可归因的遍历成本优化。安装候选、WSL Remote 与人工长时间使用仍属于 C4 验收。

## 超过默认项目文件预算

后续核对发现，候选预筛已完整列出可能含目标名称的路径，但项目有大量无关 PHP 文件时，之前仍按所有项目文件消耗 `maxFiles` 预算。索引器已有 `skipSourceOutsideBudget` 契约：对预筛排除的文件继续检查路径和变化时间，让命中的文件及预筛后变动的文件消耗读取预算，并以 50,000 个 PHP 路径作为默认清单上限。现在只要候选预筛成功，项目来源扫描也使用该契约；没有完整预筛时仍按原预算拒绝不完整结果。

新 stdio 回归用 2 个相关文件、6 个无关文件和 `maxFiles: 2` 验证 References 返回声明与调用；随后新增第 3 个相关文件且不发送 watcher，下一次查询明确报不完整，避免静默漏引用。同一改动下，独立宿主使用 **10,050 个无关项目 PHP 文件**和真实 vendor 的默认预算，首次 References 返回正确的两个位置，命令等待 980 ms、候选预筛 41 ms、遍历 757 ms，退出码 0。相关取消、未打开新文件、交替方法证据和依赖 Implementation 不完整结果共 5 项 stdio 回归通过。这个单次大项目样本证明超过旧项目文件预算时的可用性，不是 50,000 文件或 Remote 的性能验收。

接近上限的独立夹具又加入 **49,000 个无关项目 PHP 文件**和同一真实 vendor，首次 References 两次都返回相同的两个位置，退出码均为 0。命令等待分别为 2,832/3,021 ms，候选遍历为 2,501/2,655 ms；第二次查询后 Language Server RSS 为 260 MiB。这是两个冷进程的端点样本，尚未量出运行期间峰值或交互 P95，不能替代 C4 的正式 50k、长会话与跨平台门禁。它显示正确性继续保持，而大项目首次等待主要仍在遍历被预筛排除的文件元数据。

为定位这段遍历，测试模式又记录第一个文件进入处理前的目录清单阶段。同一 49,000 文件夹具的独立冷进程返回正确两个位置，总等待 2,929 ms；候选预筛 127 ms、目录清单至首个进度 583 ms、候选索引合计 2,529 ms，查询后 RSS 263 MiB。索引总时长减去首个进度约 1.95 秒，主要是后续逐文件元数据检查和循环开销。当前证据不支持删掉变化核对；若要更快，需另外建立可证明完整的候选快照协议，而非把未检查文件当成不存在。

## 有界元数据工作线程

为了保留逐文件变化核对，同时减少 Node 异步 `stat` 的调用成本，先在独立临时目录对 12,000 个 PHP 文件做方法对照：128 并发的 Promise `stat` 用时 725 ms，工作线程分批执行同步 `stat` 用时 141 ms。这个微基准只用于选择实现方向，不是 SoPHP 查询延迟。

现在候选清单达到 1,000 文件时，索引器可使用语言服务器提供的元数据检查器；该检查器在独立工作线程中每批最多检查 128 个路径，返回每个文件的大小、修改时间和状态变更时间。检查仍发生在候选扫描期间；缺失、权限错误、工作线程异常或回复不完整会使相应文件检查失败，最终查询保持不完整，不会把它当作无关文件。小清单、非候选扫描及工作线程无法同步创建时继续使用原有异步 `stat` 路径。

使用同一 49,000 噪声文件和真实 vendor 的隔离 VS Code 1.139.0 Linux x64 源码宿主，首次 References 返回相同的两个正确位置，退出码 0；命令等待 1,515 ms、服务器 1,320 ms、候选预筛 131 ms、候选索引 1,145 ms、其中目录清单至首个进度 677 ms，查询后服务器 RSS 269 MiB。与上面的 2,929 ms 冷进程样本相比，主要改善来自逐文件元数据阶段；进程与文件缓存不同，不能把两次端点差值当作稳定 P95。索引包 41 项测试、候选预算/外部预筛/portable Implementation 的 3 项真实 stdio 测试、类型检查、相关 ESLint、扩展 bundle 构建及差异检查通过。安装 VSIX、Remote 文件系统和长会话仍未验收。

第二个独立 49,000 文件冷宿主也返回相同两个位置，退出码 0；命令等待 1,665 ms、候选索引 1,285 ms，查询后服务器 RSS 265 MiB。将“无 watcher 新匹配文件使预算超限”的 stdio 回归扩为 1,000 个无关文件，使它实际走元数据工作线程；初次引用正确，随后新建匹配文件的查询明确报不完整。同次还重跑了进行中的 References 被新编辑取消的回归，二者均通过。日志为 `/tmp/sophp-c1-stat-worker-repeat-20260925.log`。这些 Linux 源码宿主样本支持继续使用该实现，不能证明 Remote 文件系统上的延迟或取消上界。

随后在 10,050 个无关项目 PHP 文件加真实 vendor 的独立宿主运行 25 轮未保存接收者切换，每轮依次核对补全、Hover、参数提示、定义、实现与引用，共 150 次查询，退出码 0。References 的本机等待中位数 165 ms、P95 199 ms、最大 326 ms；其余五项均通过对应结果断言。语言服务器 RSS 起末两次采样为 337/349 MiB，不能据此推断长期内存趋势。日志为 `/tmp/sophp-c1-stat-worker-chain25-20260925.log`。测试入口显式传递 `PHP_COMPANION_TEST_C1_CHAIN_ROUNDS`，避免环境传递方式决定是否执行这条链。下一步转向 C2 未保存编辑、关闭与文件事件重叠时的诊断及类型反馈，再在候选冻结时核对 Remote 文件系统。

## 工作线程取消边界

元数据工作线程现在接收共享取消标记。查询取消时，主线程立即拒绝尚未完成的元数据检查并请求终止工作线程；工作线程在每个路径前检查标记，避免继续遍历剩余批次。取消仍由索引器的现有 `shouldContinue` 判定，不能把部分结果当成完整引用。定向工作线程测试覆盖正常元数据和取消后待处理 Promise 的拒绝；1,000 文件的新文件完整性及查询被新编辑取消的两项真实 stdio 回归通过。更新后的扩展 bundle 在 10,050 个无关文件和真实 vendor 的独立冷宿主返回相同两个引用，命令等待 723 ms、候选索引 443 ms，退出码 0，日志 `/tmp/sophp-c1-stat-cancel-cold-20260925.log`。这是另一组本机冷进程样本，不能与先前 49,000 文件数字混作同规模性能比较；Remote 文件系统取消上界仍需实际环境验证。

交付清单的只读检查 `pnpm exec vsce ls --no-dependencies` 已列出 `dist/language-server.js`、`dist/sourceStatWorker.js` 和原有候选搜索工作线程；`scripts/verify-vsix.mjs` 也将新文件列为 Core 必需资源。本轮没有生成或安装 VSIX。实际归档内容与安装后的进程启动仍留在下一次候选冻结门禁。

## 同规模温态 References

在冷查询夹具中增加可选 `PHP_COMPANION_TEST_C1_COLD_WARM_ROUNDS`，每轮检查完整位置集合与首次结果一致，并分开记录 VS Code 命令、服务器处理、候选扫描和新鲜度检查。49,000 文件、真实 vendor 的独立 Linux 源码宿主先跑 20 轮（中位 161 ms、P95 173 ms），随后另起进程跑 **100 轮**：所有位置均正确，宿主退出码 0；命令中位 **161 ms**、P95 **177 ms**、最大 **184 ms**。100 轮服务器处理的中位/P95 为 **116/128 ms**，候选扫描中位约 **0.008 ms**，方法引用新鲜度检查中位/P95 为 **111/123 ms**。冷查询后的 RSS 266 MiB，100 轮后 334 MiB；两个端点不能证明长期内存趋势。原始日志为 `/tmp/sophp-c1-49k-warm20-20260925.log` 和 `/tmp/sophp-c1-49k-warm100-20260925.log`；100 轮测试模块 `dist-test/suite/c1.js` SHA-256 为 `413f9c7efc3700c3c5aaed199d838369b97026fba637fee3fdc0a955a3726c85`。

这次分段表明温态等待主要来自每次用 `rg` 证明没有无 watcher 的新匹配文件，而不是重复建立候选索引。已有“新建未打开文件、不发送 watcher，下一次 References 必须看到或明确报告不完整”的回归要求不能通过延迟检查来放宽。下一步若要降低这段等待，需设计并验证同样完整的增量新鲜度证明；当前 100 轮数据仅是 Linux 源码宿主样本，不代表安装候选、Remote 或长会话性能门槛完成。

## 当前源码复测与优先级

2026-09-25 再用当前源码、锁定的真实 vendor 和 10,050 个无关项目 PHP 文件运行独立 Linux VS Code 1.139.0 Core 宿主。首次 References 在 666 ms 返回相同的两个正确位置；服务器 529 ms，候选预筛 46 ms，候选索引 442 ms，其中目录清单至首个进度 308 ms，候选代次重试 0。随后 20 次温态结果集合均相同，命令中位/P95 为 71/77 ms，方法新鲜度核对中位/P95 为 41/46 ms；进程退出码 0。日志 `/tmp/sophp-c1-current-10k-cold-warm-20260925.log`。

本轮没有改动索引器。10k 当前源码样本没有暴露新的错误或比原有同规模证据更高的等待；49k 冷查询仍有约 1.3 秒中位基线，Remote 文件系统仍待 C4。保留逐文件元数据和无 watcher 新文件核对的完整性约束，把实现时间先用于已知的编辑体验缺口；若后续真实操作发现不可接受的等待，再按同规模、同环境对照优化。
