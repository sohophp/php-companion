# C2 按需索引中的当前文件 `never` 诊断

日期：2026-09-24。Open Source Pack 默认 `onDemand` 组合此前在 `ControlFlowDiagnostics.php` 只显示 7/10 条不可达语句，缺少同一文件中 `stopNow(): never` 调用后的三条。原语言服务器只有在整个 Composer 项目与依赖索引都完整时才向控制流分析传递已证明的 `never` 调用。按需索引不会主动完成整个依赖树，因此即使声明和调用都在当前文件也被抑制。

现在 PHP 8.1 以上的诊断在完整索引下沿用原语义结果；索引不完整时，只接纳**当前文件内、唯一解析、参数兼容的原生 `never` 函数**。跨文件函数、方法、PHPDoc `@return never`、参数不兼容和无法证明的短路调用仍保持未知，不据此报告后续代码不可达。SemanticWorkspace 保留原完整索引行为，并为不完整索引增加局部证明选项。

验证：SemanticWorkspace 完整测试 **305/305**、语言服务器分析测试 **41/41**；真实 stdio 的 `onDemand` 正反例通过，覆盖同文件直接、嵌套、参数与条件调用，以及跨文件函数和不兼容参数。独立 Composer 夹具的隔离 VS Code 1.139.0 源码宿主，在显式 PHP 8.5 和默认 `onDemand` 下观察到预期 **10/10** 条不可达诊断，退出码 0。`pnpm test:extension:c2` 可重新构建并运行此宿主门禁；本轮已构建后直接运行等价的宿主入口，未重复构建。改动文件 ESLint、TypeScript 构建和差异检查通过。

源码宿主的大套件因原夹具 Composer 约束 `>=7.2` 会把 auto 模式解析为 PHP 7.2，先前对 PHP 8.1 `never` 的期待与目标版本冲突；现在大套件临时工作区显式选择 PHP 8.5，基础夹具保持 PHP 7.2 可用。大套件已越过 10 条诊断断言，但随后在“删除未使用私有参数”重构动作检查处失败，故本轮不声称大套件全过。原因仍待 C3 单独定位。

此轮不修改外部业务项目，也不重新打包 VSIX。`c280d1c5` 的私有 Alpha 候选早于本修复；在下一次组合冻结前不能用它验证本源码结果。Remote、其它系统、长期会话和跨文件按需证明仍为后续验收项。
