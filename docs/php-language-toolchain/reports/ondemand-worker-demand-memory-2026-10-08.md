# onDemand 内存阶段取证与候选 worker 按需启动

2026-10-08。修正已接入正常源码与生产构建：候选 worker 在现有 worker 全忙时按需求启动，小扫描复用空闲 worker；繁忙工作仍可使用原四 worker 上限，不缩减候选扫描或查询支持范围。原回复归属、异常回退与关闭逻辑保持。严格类型、Lint、正常两文件12项 worker 单元通过；原实现对新增回归有4项失败，失败记录保留。详见[机器证据](ondemand-worker-demand-memory-2026-10-08.json)。

## 原始内存失败与阶段定位

此前正常构建的原始1,000次编辑／恢复，RSS增量139.125 MiB超过128 MiB，原失败继续保留。随后只执行一次有区别的被动诊断，保留100次预热、1,000次正式编辑、500噪声函数、PSR-4、全部查询和断言；剥除阶段记录后与原脚本逐字相同，不新增LSP请求、不强制GC、不放宽预算。

旧构建诊断的阶段RSS为245.63 MiB基线→288.45 MiB编辑结束→358.43 MiB引用与符号查询结束。首次引用前后增加69.86 MiB，同时出现一个source-stat与四个candidate worker。主线程external在编辑期间约34 MiB，old-space已用量从27.20升至56.49 MiB；主线程在基线后只记录到minor GC，没有major GC，因此不能证明这部分是实际保留或泄漏。

首次观测预检遗漏worker，原因是Node加载require预处理器时worker尚无入口参数。独立原生小程序复现后，改为worker第一个immediate登记入口；修正预检证实主／worker独立文件与阶段确认。原失败保留，正式产品诊断未重跑求绿色。worker最初同步分配缺少细分计时，RSS属于整个进程，external已包含arrayBuffers，均不可简单相加。

## 因果控制与隔离候选

真实native worker对照验证：旧实现串行两个任务启动4个、仅使用1个；两个并发任务启动4个、仅使用2个。候选分别启动1／2个，九个排队任务仍启动并使用4个；全部26个任务返回内容逐字一致，全部native线程终止。单元额外覆盖restore／prepare／compress复用、CPU约束、构造失败、单worker退出与发送失败后的归属释放。

原完整编辑流程的候选被动诊断中，首次引用使用两个candidate worker、恢复进程使用一个；首次引用阶段新增RSS为46.05 MiB。两场被动诊断的整轮结束减基线分别为112.84／116.02 MiB，基线不同，不能据此声称整轮内存改善或把诊断退出0作为普通资格。

原10项生产协议在候选通过，覆盖PHP7.2／8.5、onDemand／progressive／experimental、新文件、未打开文件变化／删除及system／portable／off搜索；实际十个服务器绑定候选运行资产并全部正常退出。原断言、请求与期限保持，不替代完整LSP或编辑器资格。
