# 引用缓存：不完整 Provider 的输入证据与方法预热恢复

日期：2026-10-01。源码工作；未打包、提交、推送或更新 Profile。

## 两个已复现问题

1. 跨进程引用缓存的额外 bundle 用例在新增 `services.yaml` 后失败。该配置导入不存在的 `missing.yaml`；Symfony Provider 因服务事实不完整返回 `complete=false`。进程宿主拒绝语义贡献时也丢弃了已知的配置及负查找路径，引用证明的输入证据随之缺失。
2. 第一个修复通过原失败步骤后，后半段发现已预热的方法引用仍再次扫描候选。光标预热加载了方法，引用入口用“已经解析为方法”排除了提前恢复；之后虽恢复了正确缓存，额外候选扫描已经发生。

## 实现

- `SemanticProviderRunResult` 的失败分支可携带独立的 `containerInputEvidence`。只有完整协议校验通过、请求 ID／Provider 身份／generation 一致但事实不完整的响应可以提供它；无效协议、身份不匹配、超时和崩溃没有此证据。
- 只提取读取 URI、配置 URI和输入完整性，不返回可提交的语义贡献。服务、方法、属性等不完整事实继续被拒绝。
- 语言服务器仍检查请求时效并清除旧容器事实，再把已知读取路径记录到输入证据表。不把这些路径登记为已接受的服务语义配置。
- 方法已经解析时也允许尝试 `restoreReferenceResult`。恢复函数继续核对引擎、Provider 文件、环境、源码、缓存指纹、请求代次和输入完整性；没有放宽缓存校验。
- 跨进程用例保持所有位置、恢复／失效、无重复候选扫描和负查找断言。组内 32 次启动的总时限从 60 秒调整为 120 秒；单请求仍为 10 秒，增加失败时的 run 编号及证明诊断。
