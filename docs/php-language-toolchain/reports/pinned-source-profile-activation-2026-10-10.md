# 固定源码组合的激活验证及尚未解决的等待（2026-10-10）

已有十二扩展源码组合现在使用每轮新建的安装扩展副本与用户目录，关闭隔离编辑器和扩展的自动更新，并在宿主内校验配置。PHP7.2/progressive/10k 的单轮首次 Completion、Hover、Definition 严格正确，十二项 ID、版本和加载路径匹配，退出后安装扩展运行文件摘要不变。正常八运行资产与原激活时钟、查询断言未改，日常 Profile 未更新。

## 两个原失败保留

原 405 轮组合矩阵实际执行 21 轮，20 轮及其 60 次首次查询通过；第 21 轮在首次查询测量之后的组合清单校验中失败：期望 xdebug.php-debug 1.40.1，实际为 1.40.2。原日志明确显示编辑器自动升级该隔离副本中的 PHP Debug 和 YAML 扩展。来源安装目录与正常运行资产保持，原矩阵继续为失败，384 轮未执行。该失败轮的首次查询原始响应当时没有单独持久化，不能把它计入已验证的 60 次查询。698 个失败文件保留。

第一次关闭更新后的验证也保持失败：该 VS Code 1.140.0 的实际配置 schema 将 extensions.autoUpdate 定义为 on/off 字符串，原布尔 false 被迁移为 off，测量器错误地断言布尔 false。三次首次查询已正确且单独持久化，失败来自后续观察断言；55 个文件及实际编辑器 schema 摘要保留。现使用规范值 off 并严格核对，同时核对 autoCheckUpdates=false 和 update.mode=none。没有放宽扩展版本、路径或查询断言。

## 性能问题继续

约 40 秒的首次补全仍未解决。服务器日志显示初始索引后又因 semantic-provider-change 执行第二轮索引；正常服务器的 Completion 与 Completion Resolve 在查询前等待全局 semanticProviderReconciliation，而 Symfony 注册的协调任务等待原索引结束再执行替换索引。这解释了该普通 PHP 查询等待约两轮索引的路径，后续需验证并修复等待范围，同时保持框架事实的正确性、撤销、并发及取消行为。

本轮证明隔离组合固定、首次查询正确及退出清理；不宣称激活性能通过，也未将原 405 轮失败改写为通过。[此前完整 Linux Core 观测](editor-activation-full-linux-core-matrix-2026-10-10.md)保持独立。完整组合矩阵、其它平台、真实 WSL、自然 UI、长期使用及原全部功能范围继续，未安装、打包、提交、推送或发布。
