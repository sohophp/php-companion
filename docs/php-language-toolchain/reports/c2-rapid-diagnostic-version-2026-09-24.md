# C2 快速编辑时的旧诊断发布

日期：2026-09-24。独立 Composer 项目、PHP 8.5、默认 `onDemand` 下，隔离 VS Code 1.139.0 源码宿主在同一未保存文件中快速切换 `stopNow(): never` / `void`。最后一次编辑为 `void` 后，原测试观察到诊断事件的不可达提示数仍短暂回到 10，再变为正确的 7。服务器原本为标准 LSP 诊断附带文档版本，但当前语言客户端的诊断队列只保留 URI 与诊断数组，应用时无法再比较版本。

SoPHP Core 现在与自己的语言服务器使用带版本的诊断通知。客户端在转换前后都核对打开文档的身份和版本，只把匹配当前缓冲区的结果写入 SoPHP 诊断集合。PHP 内容变化时先撤下该集合里的旧诊断；新结果到达后再显示。独立 stdio 客户端未启用此选项时继续接收标准 LSP 诊断；文件关闭仍由标准空诊断清理。此边界不会改变 VS Code 内建 PHP 验证或其它扩展的诊断集合。

验证过程：仅按接收时版本过滤仍观察到最后一次编辑后的旧 10 条事件，因为旧结果可能在编辑前已写入集合；加入编辑时撤下后，隔离宿主连续两轮通过 20 次快速切换加最后一次 `void` 编辑。最后一次编辑之后仅观察到集合清空和正确的 7 条结果，没有旧 10 条；最终可见结果为 7，缓冲区保持未保存，退出码均为 0。源码 Core + Symfony Extension Host 完整套件退出码 0；定向 stdio 证明版本通知包含文档版本，内容变化后会更新，关闭文件会清理。TypeScript、ESLint 与差异检查通过。

编辑后的短暂清空是当前明确的反馈方式。随后在同一源码宿主门禁中，对 20 次快速切换后的最后一次编辑做了三次计时：从清空到正确 7 条诊断出现约为 268、279、319 ms；从最后一次编辑开始到正确结果出现约为 312、298、335 ms。新增测试模式服务器计时的一次复测中，宿主诊断空白为 444 ms、正确结果等待 456 ms，而服务器处理该次文档变化和诊断发布分别约为 26、22 ms。

进一步在测试宿主记录客户端发送、接收和写入诊断的时间戳：增量编辑从客户端发出只需约 1 ms，但最后一次编辑后，客户端仍按顺序收到约 10 个旧版本的诊断通知，每个约隔 25 ms；它们因版本检查未写入诊断集合，最终版本的正确结果仍排在通知队列后。服务器现在对文档变化后的诊断分析短暂合并 25 ms，让连续编辑先更新到最新版本；文件打开仍立即分析。相同快速编辑宿主三轮复测中，最后正确结果等待为 109、111、120 ms，诊断空白为 100、67、64 ms，最终均为 7 条且无旧 10 条回闪。三轮中服务器最终版本诊断发布约 42–50 ms，包含 25 ms 合并等待。真实 stdio 回归又将 20 次编辑连续送入服务器，断言只发布最终版本 22；紧接着编辑并关闭文件，断言旧版本 23 不再发布且标准空诊断完成清理。该定向回归连续三次通过，单次编辑的版本通知也通过。语言服务器套件 18 个文件、323 项通过、1 项跳过；完整源码 Core + Symfony Extension Host 退出码 0。以上是事件时间而非物理屏幕像素测量，样本少，不作为跨平台延迟分布。

真实 Profile、长会话、Remote 和其它系统仍需验收。此修复尚未进入先前 `c280d1c5` 私有 Alpha 候选，本轮没有重新打包 VSIX，也未修改业务项目。
