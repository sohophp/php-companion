# D136 Composer 项目探测的迟到结果保护

## 可复现错误与修复

现有 Workspace 目录代次保护不能区分同一目录内的两次文档探测。受控复现证明两种错误：冷文档读取新 Composer 快照并发布 8.5 后，旧探测把状态覆盖成 7.2；两次 Composer watcher 刷新也出现相同覆盖。初始 7 项中原五项通过、新两项失败。

在目录代次之外增加 Composer 项目代次。全局／目录刷新和文档探测发布前都验证自己的项目代次；新 Composer 文件通知立即撤下旧探测资格与项目缓存，不等 250 ms 防抖结束。防抖后的探测仍只覆盖该项目，缓存已由即时查询更新时可直接复用。dispose 清理项目代次，迟到结果不发布。

同一 Workspace 下不同 Composer 根保持独立；嵌套项目变化不使父目录正在进行的刷新失效。不改变版本解析优先级或默认 CLI，也不修改被测业务项目。

## 正式证据

- 原两种覆盖在修复后通过，扩充到 10 项受控交错均通过：即时通知失效、两嵌套项目、嵌套 watcher 与父刷新并发，加上原刷新／移除根／dispose 反例。
- 根扩展完整单元门禁：20 文件／103 项全部通过，零失败或跳过。之后只给测试 mock 补显式返回类型注解；产品源代码未变，类型／Lint 单独核验。
- Linux VS Code 1.140.0 Core 源码宿主最终退出 0：指定 PHP 8.5 主项目，执行该配置适用的 C1 查询、未保存接收者变更、vendor、跨根设置及移除根检查。复核脚本后确认，`if (!targetPhpVersion)` 内的 Composer 自动版本、platform 修改和嵌套项目分支没有执行；本次宿主不能证明这些分支通过。嵌套并发保护在本批由受控单元证明，自动模式宿主另行验收。状态栏文本通过现有测试命令读取，不冒称已截图核验真实 WSL 状态栏。
- 同一宿主原 12 个串行热命令样本：首次补全 121 ms；补全最大 15 ms、References 最大 101 ms。样本数量与指标保持，不当作普通持续编辑 P95 或全部规模预算。
- 根 TypeScript、宿主 TypeScript、变更文件 ESLint、production bundle 和差异空白检查通过。最终宿主的八项记录输入哈希保持，bundle `dist/language-server.js` 与 D135 逐字节一致；本批只改变扩展端版本协调和验收工具。

本批 source host 未强制重排真实 CLI 子进程完成顺序；精确竞态由受控单元证明，宿主用于组合操作保持。Windows/macOS、真实 WSL、多小时会话、全部 PHP CLI 与规模矩阵继续开放。

## 宿主阻断与修正历史

首轮宿主在到达版本切换验收前失败；增加观测后第二轮仍失败。原断言要求分组导入替换范围包含花括号，而当前语义已使用单词范围。观测实际为替换 `c1_mix`、插入 `c1_mix_function`，花括号留在原文，接受文本没有被破坏。

统一修正同类五处断言：检查实际 range／insertText 产生的完整最终文本，保留其他成员、namespace 前缀、花括号、候选类别、无额外 use 及原实际编辑器接受检查。没有改产品来满足旧范围形状，也没有跳过失败操作；第三轮既有完整 C1 通过。原两轮失败与实际返回值另存，见同名 JSON。

首次新增 watcher mock 的 Lint 缺返回类型，补类型注解后最终 Lint 通过；不掩盖原结果。
