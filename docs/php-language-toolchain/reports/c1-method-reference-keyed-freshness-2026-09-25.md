# C1：交替方法查询的 References 候选复用

日期：2026-09-25。仅修改 SoPHP Language Server、隔离测试与文档；未修改业务项目，未打包 VSIX。

## 原因与修复

在 10,130 个 PHP 文件的独立 Composer 夹具中交替编辑两种接收者方法时，References 结果正确，但重复等待约 0.6 秒。分段计时先证明，修复前的 50 轮只有 **1 次**执行候选路径新鲜度搜索（约 40 ms）；其余温态查询没有拿到可复用的证据，因而重复完整候选扫描。

候选覆盖本来按方法查询键保存，但用于验证覆盖的新鲜度读取证据只保存最近一次扫描。两个方法交替时，后一个方法覆盖前一个方法的证据。现在按查询键保存最多 8 份方法证据；打开的未保存文件变化后，只把同一项目根、上一候选版本且已经迁移覆盖的证据同步到新版本。每次复用仍重新搜索候选路径、校验命中文件内容和已加载旧候选；新增未打开文件会使旧证明失效并触发完整扫描。持久化引用结果仍使用独立的输入证明。

## 验证

| --- | ---: | ---: | ---: | ---: |
| 六项查询结果 | 全部正确 | 全部正确 | 全部正确 | 全部正确 |
| References 中位等待 | 669 ms | 137 ms | 125 ms | 123 ms |
| References P95 | 849 ms | 180 ms | 174 ms | 171 ms |
| 新鲜度搜索记录数 | 1 | 49 | 199 | 最近 256 次¹ |
| 新鲜度搜索中位耗时 | 40 ms（单次） | 40 ms | 41 ms | 41 ms¹ |
| 宿主退出码 | 0 | 0 | 0 | 0 |

修复后 200 轮共产生 1,200 次真实 VS Code 六项查询，全部通过。语言服务器 RSS 从 314 MiB 到 329 MiB；这段数据不能证明数小时会话或其它平台的内存上界。日志分别为 `/tmp/sophp-c1-freshness-profile-20260925.log`、`/tmp/sophp-c1-freshness-keyed-20260925.log`、`/tmp/sophp-c1-freshness-keyed-200-20260925.log`。

修复后 1,000 轮共产生 6,000 次查询，全部通过。每 25 轮一次的语言服务器内存采样：RSS 起始 327 MiB，前半段升至 363 MiB，第 625 轮后堆使用量从 122 MiB 降至 36 MiB，第 775 轮 RSS 降至 303 MiB，末轮 RSS 304 MiB、堆 55 MiB。这说明前 500 轮的单向上升不足以判定泄漏；仍不代表数小时会话或其它项目没有泄漏。日志：`/tmp/sophp-c1-freshness-keyed-1000-20260925.log`。

¹ 测试模式的计时列表按指标最多保留最近 256 次；1,000 轮栏中的新鲜度搜索统计是末段样本，不是搜索总次数。

新增 stdio 回归让两个不同方法在同一未保存调用文件中反复切换，断言各只扫描首次一次，且引用始终指向当前调用；定向通过。既有“新建未打开文件经文件事件进入 References”和“打开文件变化刷新接收者证据”两项 stdio 回归也通过。Language Server 类型检查、改动文件 ESLint 与差异检查通过。

完整 Language Server stdio 文件测试 **167 通过、1 跳过**，退出码 0；日志为 `/tmp/sophp-c1-keyed-stdio-full-20260925.log`。

已知等待：本机 10k 夹具每次温态 References 仍需约 40 ms 新鲜度搜索，完整命令中位等待约 123 ms；首次冷扫描仍更慢。下一步在不削弱新文件立即可见的条件下降低其余开销，并在已安装候选、WSL Remote 和真实编辑器中复核。本轮仅是 Linux 源码宿主证据。
