# D123 缓存生命周期诊断与压缩传输实验

日期：2026-10-06；检查点 `3dd112ae`，产品为 D121／语义 schema 88，根 bundle SHA-256 为 `64793c2152b39eeb152883af8c06218fd1695adb3beee395274ef9676d7aba12`。本轮没有修改产品、原持久缓存基准、缓存格式或预算。[结构化记录](cache-transport-memory-2026-10-06.json)包含完整脚本、结果、退出状态和来源摘要。

## 生命周期诊断

在原持久缓存基准的私有副本中，仅增加阶段内存、workspace 容器数量和大 JSON 读写观察。10k 同一进程完成冷索引、全量热恢复、派生层损坏恢复、callable 损坏恢复及清理，功能断言保持，退出 1。

冷阶段高水位约 310.71 MiB，首次热恢复结束前高水位约 491.27 MiB；完整序列最终高水位 **997.01 MiB**，超过原 768 MiB 预算。两次损坏修改均读取并序列化约 57 MB 的完整 JSON，后续恢复又读取完整文件。观察点显示较大的阶段上升发生在这些操作附近。

各 workspace 在 `dispose()` 后，可观察的主要 Map／Set 均为空，仅保留至多 512 条变更历史；共享清理方法也清除 callable 依赖和引用结果缓存。这没有证明某个对象泄漏或 GC 异常；带观察包装的结果也不是正常性能资格。未做堆快照、强制 GC 或全局配置修改。

## 一次不同的传输实验

复用当前 `projectFacts` 已有的逐文件 deflate 压缩与有限解压。默认 progressive 缓存和 onDemand 定向缓存已经使用该格式；原通用持久缓存基准保存未压缩 payload。本实验核对压缩传输对**完整原序列**的影响，不宣称为已实现的新产品修复，也没有扩大 experimental 模式的正式行为。

私有副本添加同一个 `finalizePayload`，恢复时先有限解压。两种损坏仍修改同一文件的相同语义记录，并保留原校验和不更新，再压缩回原 entry；不绕过校验或减少恢复阶段。所有原断言保留，同一进程包括语料生成、四次加载、两次整 manifest 读写和最终清理；未强制 GC、拆分阶段、提高预算或重复失败轮。

| 10k | 21257.57 / 7396.33 | 25.23 / 512 | 518.40 / 768，通过 | 0 |

两规模全部热恢复，无热重解析，Doctrine／三个 callable／构造依赖恢复正确；聚焦查询只加载四个关联文件，消费文件仅加载 `Consumer::inspect`；派生失效正确，两种损坏各只重解析一个文件，恢复后补全与构造事实均正确。50k 功能通过不能覆盖内存失败，10k 单次通过也不能代表整个规模资格。

## 结论与后续边界

逐文件压缩降低了本次序列的缓存体积，但没有使 50k 完整内存门槛通过。没有保留只在 10k 达标的产品增量，不再重复本方案或 D119 流式 JSON 方案的等价测量。正式产品摘要和源码保持，D122 的既有组合验收仍绑定原产品。
