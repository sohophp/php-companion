# C1 嵌套 Composer 项目的按需识别

日期：2026-09-24。一个 VS Code 工作区根下可以包含独立的 Composer 子项目。此前语言服务器的 experimental 模式扫描项目根后能把同名类分开，但 onDemand 模式只登记工作区根；打开子项目文件后，补全返回空结果，并可能沿用父项目的 PHP 目标版本。

onDemand 现在按打开或查询的文件向上寻找最近的 Composer 根，给新发现的子项目建立独立语义工作区。项目源文件仍按需加载。已安装的 vendor 包即使带有自己的 `composer.json`，只要它属于父项目的锁定依赖，就继续归属父项目。VersionManager 不再用子项目状态覆盖工作区根状态；扩展把已识别子项目的解析版本送给服务器，并在版本状态变化后重新加载语言服务器。

真实 stdio 的 F04-NAV-15 在 experimental 与 onDemand 两种模式下验证同名类补全落到子项目，父根 PHP 7.2 和子根 PHP 8.5 的版本诊断各自正确。F04-NAV-16 在 onDemand 模式下先打开带 `composer.json` 的 vendor 声明，再从该声明查询 References，确认能找到父项目中的调用。隔离 VS Code Core 宿主在 auto 模式下验证子项目补全、定义、引用和 PHP 8.5 诊断；随后新打开的父项目文件仍按 PHP 7.2 诊断。auto 与显式 7.2、8.1、8.5 四次宿主运行均退出码 0，相关 TypeScript 与 ESLint 检查通过。

首次全套回归发现一个时序问题：文件内容变更事件在异步寻找项目根时让出执行权，随后到达的 References 请求可能先复用旧结果。现在用上一次收到的文档文本判断是否真的变化；变更文本先使引用候选失效，再进行项目根与语义更新。打开文件带来的首次内容事件和同文本版本更新不撤销已有源码准备；progressive 模式的非声明编辑继续保留准备结果。旧结果竞态、experimental/progressive 源码准备复用及嵌套/vendor 的定向用例共 6 项复测通过。Language Server 全套回归为 307 项通过、1 项跳过；最终构建后的隔离 Core 宿主在 auto 和显式 PHP 7.2 下再次退出码 0。

此证据覆盖打开文件触发的嵌套项目发现，不代表已经验证所有 Composer 路径仓库、符号链接、运行时探测、虚拟内建声明文档和大型项目的延迟。实际建议弹窗显示时间、Remote 和完整 Open Source Pack 组合仍开放。未修改业务项目，未打包 VSIX。
