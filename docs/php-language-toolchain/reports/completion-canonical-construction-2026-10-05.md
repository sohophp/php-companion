# D103 可证明的跨文件构造诊断

日期：2026-10-05；基于 `99b231b7`，继续 C1／C2 常用构造补全及诊断。没有打包、推送或更新 Profile。

## 实现

- 语义层按诊断的精确名称／参数值范围找回所属 `new` 调用，取得实际实例化目标、构造签名及唯一完整的父类／接口／Trait 图。内外层调用共用同一 Trait 构造来源时，仍分别归属正确目标。
- onDemand 服务器沿完整依赖图检查 Composer 来源：唯一 PSR-4 路径或有效生成的字面量 classmap 必须指向当前声明文件。当前调用文件的声明和可信内建依赖保留；内建构造诊断继续由原入口负责，避免重复报告。
- 直接 Trait、嵌套 Trait、继承、构造方法别名、可解析的 precedence 和普通外部类构造复用同一证明。动态目标、重复声明、缺失依赖、循环、构造冲突及无法证明的路径继续撤回。
- 异步读取 Composer 证据期间若源码版本改变，撤回旧构造诊断。保留普通方法的原可见性／final／精确接收者证明；外部参数类型检查继续遵守原标量／唯一原生标量返回值限制。
- 不改变持久化事实结构，缓存合同保持语义 **86**／源码声明 **4**。新增暂停入口只在测试模式生效。

## 原失败及修正

1. D102 原产品的 baseline 为 0／6：onDemand 三项复现外部 Trait 构造缺参漏报；完整模式另外三项揭示新测试对未知命名参数和虚拟 static 签名的预期不符合现有合同。更正测试，保留原日志，不将后者计作产品修复。
2. 首轮 4／6 的两项失败来自 PHP 7 的 `ArrayObject` 输入没有此处原生类型底线。保留现有未知行为；PHP 8 的原生底线仍只报告一次。
3. Composer 证据轮 12／14 的两项失败来自假 classmap 夹具不符合生成文件的字面量格式。改为实际 Composer 格式后通过；未扩大执行或解析任意 PHP 的范围。
4. 删除版本保护的临时对照为 0／2，准确触发旧证明仍被保留的断言。当前源码两项为 2／2；该对照是预期失败。
