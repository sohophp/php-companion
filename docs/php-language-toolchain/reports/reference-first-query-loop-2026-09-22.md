# 首次 References：缩短验证循环与瓶颈复核

本轮以 Winstar 源码为只读样本，查询 `AdminPasswordChangeGuard.php` 最后一个 `get`，启用 Symfony Provider。每次使用正式 bundle、独立空缓存，先发 References，再核对结果数量和排序后的位置 SHA-256。目标是定位首次查询的实际关键路径；此报告不代表 WSL 编辑器交互验收。

新增 `scripts/benchmark-first-references.mjs`，把单次冷查询、阶段日志提取、结果哈希及可选基线对比合成一个命令。候选和基线各使用独立临时缓存；结果数量或位置哈希不同则直接失败。快速迭代先跑单次候选，只有观察到稳定收益时再交叉复测，避免每个猜想都等待四次完整冷启动。

```bash
PHP_COMPANION_BENCHMARK_SYMFONY=1 \
PHP_COMPANION_EXPECTED_REFERENCES_SHA256=bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2 \
node scripts/benchmark-first-references.mjs \
  /var/www/php/8.5/winstar2024 \
  /var/www/php/8.5/winstar2024/src/Security/AdminPasswordChangeGuard.php \
  get last dist/language-server.js
```

同一工具末尾可加基线 bundle 路径，自动对比引用集合。`PHP_COMPANION_BENCHMARK_RSS=1` 可输出进程峰值内存。此命令复用已有 `benchmark-language-queries.mjs` 的 LSP 流程，不绕过真实语言服务器。

当前正式 bundle 的单次测量：首次 References 9,043 ms、112 处，位置哈希 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2`；候选扫描 4,593 ms，容器事实 791 ms，路由 810 ms，事件 37 ms，语义引用 2,085 ms。容器和路由任务有重叠，阶段数值不可直接相加。候选扫描完成后的缓存等待 27 ms，连同写盘约 263 ms，不能解释主要耗时。

本轮对三个低风险假设做了冷查询验证，结果均保持 112 处及相同位置哈希，但没有稳定速度收益，因此未保留产品实现变更：跳过新文件的语义表面比较（旧版 9,016/9,578 ms；试验版 9,040/9,120 ms）；直接使用已解析成员访问事实筛选候选（单轮 9,103 ms，语义阶段 2,344 ms）；候选解析 worker 从 4 增至 6（对比 8,992 → 9,293 ms，候选阶段 4,482 → 4,679 ms）。这些数据表明当前机器上的瓶颈不是单一序列化、文本匹配或 worker 数量。

后续应针对候选准备和语义解析做更细的 CPU/等待分解，再修改算法；保持完整位置哈希、首次冷查询和取消/编辑失效行为作为接受条件。当前首次立即查询仍约 9 秒，未达到满意水平，Goal 继续。

## 后续分段采样

对同一冷查询再做正式 bundle 采样（8,871 ms，112 处及上述哈希不变）：`indexComposerSources` 处理 2,289 个项目文件，目录枚举 273 ms，预取等待合计 608 ms，逐文件应用合计 3,286 ms，缓存提交约 253 ms。另一轮更细的采样中，逐文件应用合计 3,425 ms；其中 `onSource` 1,691 ms，语义工作区更新 974 ms，快照创建 321 ms。计时埋点均已撤回，未加入产品运行路径。

未压缩 bundle 的 CPU profile 显示四个候选解析 worker 在该请求期间大部分样本为空闲，主线程出现 worker 消息反序列化、语义工作区更新和成员解析热点。将 PHPDoc 查找改为范围二分搜索的一次 A/B 测试为 9,248 → 9,232 ms，未达到稳定收益；预先跳过不含目标名字的 worker 任务，两组交叉测量中新版 8,938/9,178 ms、原版 9,055/9,065 ms，也处于波动范围。两项试验均已撤回。

下一阶段重点是减少短名字（例如 `get`）冷查询需要准备的声明文件数量，并在只读项目、包含继承与跨文件接收者类型的语料上核对完整位置集合。单纯增加 worker 或减少缓存写入，按本轮分段数据不足以解决首次约 9 秒的等待。

对同一 `get` 查询加临时声明访问计数后，语义引用阶段进行了 14,296 次 `fileAndDeclaration` 查找，但实际只触及 1,203 个延迟声明文件中的 24 个；首次查询 8,968 ms，112 处及位置哈希不变。埋点已撤回。这支持把延迟声明文件先保留为已准备的事实，按查询实际访问的类型再应用到工作区；实现前必须保证找不到类型时仍能保守回退，且跨文件继承、非 PSR-4 声明、开放编辑缓冲区及缓存恢复都不漏引用。现阶段不能仅凭 24/1,203 的单一语料数据跳过其余声明。

## 浅层声明与查询内缓存试验

实现过一版浅层声明注册：候选扫描时只登记解析器提供的原始声明，实际查到类型时再补齐 PHPDoc 与成员事实；缓存恢复保守地重新解析声明。Winstar `get` 首次查询的候选阶段由基线 4,792 ms 降到 4,295 ms，完整位置集合不变，但事件相关性检查会逐个访问已注册服务类并触发延迟补齐，事件阶段从约 35 ms 升到 1,633 ms，总耗时从 9,235 ms 升到 10,727 ms。加入只排除已证明无继承、接口或 trait 关系的预筛后，事件阶段降到约 0.3 秒；交叉测量仍出现新版 9,460 ms、基线 8,834 ms。该方案未表现出稳定总收益，已撤回。

另试过仅在一次 References 计算中缓存 `fileAndDeclaration` 查找，并在相关文件事实更新时失效；语义阶段约 2,156 ms，对照约 2,189 ms，处于测量波动范围，亦已撤回。两条试验均保持 112 处及相同位置 SHA-256；聚焦的 stdio 测试通过。它们表明延后声明工作和局部查找缓存没有消除关键路径，下一步应评估查询前可复用、有限时且可取消的项目准备，以及点击发生在准备过程中时的实际等待时间。不能把后台提前消耗的 CPU 时间表述为计算量减少。

## 项目预索引和重载成本

Winstar 2,289 个项目 PHP 文件，用现有 `indexComposerSources` 和完整语义更新做一次项目范围预索引，耗时 15,850 ms（不含完整扩展的 Doctrine/Symfony 分析）。把语言服务器直接切到现有 `experimental` 后立即发 References，查询仍为 9,575 ms、112 处；后台索引与按需候选扫描同时运行，未形成可复用的单一路径。未经任务合并与取消设计，不能默认开启完整后台索引，否则可能重新出现长时间“Indexing PHP symbols”。

相同缓存目录连续启动两次 on-demand 语言服务器：第一次 References 9,457 ms，第二次 7,445 ms，位置哈希相同。第二次候选扫描已恢复 1,655 个缓存候选，但仍花 2,947 ms，之后 Symfony 容器约 0.88 秒、语义查找约 2.22 秒。当前持久化的完整 References 结果只对没有语义/路由 Provider 的模式启用；在实际 Symfony 配置下，即使等待持久化任务，重载也不能直接复用完整查询结果。下一阶段若扩展持久化范围，必须先建立 Provider 输入和版本的完整证据校验，不能直接放宽开关。

Provider 输入审查确认 Symfony 服务分析读取项目配置 YAML/XML/PHP、编译容器 XML、Composer 元数据和依赖包配置资源。现有引用输入快照此前只发现目录中的 PHP 文件，无法证明新配置文件未出现。本轮扩展快照的可选文件扩展名选择，并测试 YAML/XML 的新增、修改及选择集变化会改变指纹；默认仍只选 PHP。Winstar `config/` 的 41 个匹配文件做一次完整快照约 37 ms。这个基础设施尚未使带 Symfony Provider 的结果缓存可用：仍需完整记录 Provider 命令/构建身份、所有实际与潜在配置目录、环境选择及其外部依赖，并验证结果缓存恢复时这些证据未变化。

把基准驱动的索引模式切为现有 `experimental` 并在 `initialized` 后等待 20 秒，Winstar 的首次点击仍需 15,407 ms；日志显示查询又启动了 2,289 文件候选扫描（11,575 ms），与尚未完成的完整索引争用资源。`discoverComposerRoots` 在此工作区只发现一个根，不能将延迟归咎于多项目发现。独立的项目 PHP 完整语义索引（不含完整扩展中的 Doctrine/Symfony 分析）为 15,850 ms，因此当前完整后台索引不能直接作为首次 References 加速方案。基准驱动现允许最多 30 秒的可选初始等待，便于把启动准备与点击延迟分开记录。

## 跳过非精确 token 声明的下界试验

基准驱动可用 `PHP_COMPANION_BENCHMARK_REFERENCE_LOCATIONS_PATH` 输出完整 LSP 位置数组，供两版逐项比较。临时试验完全不把 1,203 个只有 `get` 名字片段、没有精确 `get` token 的文件声明加入语义工作区；正式 bundle、空缓存、相同 Symfony Provider 下，首次 References 从基线 9,327 ms 降至 8,057 ms，但 112 处中漏掉 46 处，没有新增误报。漏项集中在依赖其他文件类/继承信息的控制器调用。试验代码已撤回。即使能零成本按需补齐全部必要声明，这一组样本的候选阶段可回收上界也约 1.3 秒，单独做声明延迟加载不足以把首次查询降到满意水平；精度优先，不能直接跳过这些文件。

## 扫描让出频率的验证

将候选索引主线程的让出间隔从每 10 个文件临时改为每 100 个文件，在同一次基线先行的空缓存 A/B 中，基线首次 References 为 8,874 ms、候选为 10,114 ms；候选扫描分别为 4,583 / 5,142 ms。两版都是 112 处，位置哈希相同。该改动已撤回，不能以减少事件循环调度次数代替结构性优化；更低让出频率还会损害取消请求的响应。下一步应把“项目候选准备、Provider 所需项目类型、语义引用查找”设计为可共享的工作单元，避免首次点击在同一批文件上重复准备事实；先以一处短名字查询建立结果集合和取消/编辑失效门槛，再扩展语料。

## 单次查询内的成员组合复用

正式 bundle 的 CPU profile 显示语义查找反复进入 `members()` 组合同一类型的继承及成员事实。现仅在一次同步 References 计算期间复用相同类型、访问作用域、可见性和模板参数的顶层成员列表；查询结束即清空，项目编辑或 Provider 更新不会跨查询复用旧结果。Winstar 同一 `get` 样本的两次空缓存 A/B 中，先跑旧版时语义阶段为 2,246 / 1,875 ms（旧/新），反向顺序为 2,308 / 2,091 ms；完整查询分别为 9,060 / 8,970 ms 和 9,528 / 9,141 ms。两组均为 112 处且位置哈希不变。收益集中于语义阶段，完整查询仍约 9 秒，不能据此称首次等待已解决。Semantic 291 项、聚焦 LSP 4 项、ESLint 和构建通过；尚未完成真实 WSL 编辑器操作验收。

## 双场景短循环

新增 `scripts/benchmark-reference-suite.mjs`，一次检查 Winstar 的短名字方法 `get` 和 Symfony 服务类 `AdminSecuritySubscriber`。每个样本独立空缓存，固定 Symfony Provider，并核对完整位置 SHA-256；可选传入旧 bundle 做结果与耗时 A/B。当前正式 bundle 单次运行分别为 9,023 ms / 112 处和 5,246 ms / 2 处。类查询的候选、容器、事件阶段约为 2.6 / 0.85 / 0.75 秒，语义阶段仅数毫秒；它与短名字方法的约 2 秒语义查找是不同瓶颈。两类工作负载必须分别通过，不能只优化一种。

把扫描并发预取从 128 临时降到 32 后，`get` 查询仍为 112 处且哈希一致，但候选阶段升到 5,929 ms、完整查询 9,994 ms；改动已撤回。后续不再单独降低预取并发，应优先让候选索引和 Provider 输入在首次查询前或查询间复用，并保证查询过程中没有第二个竞争性全项目扫描。

## Symfony 模式的跨进程结果复用

方法引用现在可以在候选扫描及 Symfony Provider 重新计算后，使用持久化的完整结果跳过昂贵的语义引用遍历。写入时记录外部语义事实及框架引用位置的指纹，恢复时要求指纹、引擎身份、Composer 输入、已加载源码与完整文件快照一致；不满足条件便正常重新计算。类查询的语义遍历仅需数毫秒，因此不做这种需要整项目快照的恢复。跨进程测试验证同输入命中，以及新增公开 Symfony 服务配置后拒绝旧结果并重算。

Winstar 的 `get` 样本同一缓存目录连续启动：首次 9,283 ms，第二次 6,553 ms，都是 112 处且位置哈希不变；第二次仍需候选恢复 2,845 ms 和容器/路由约 0.85 秒，快照验证抵消了部分语义遍历收益。新代码的独立空缓存双场景测量为 `get` 9,025 ms / 112 处、`AdminSecuritySubscriber` 5,190 ms / 2 处，位置哈希均不变。缓存尚未达到满意的首次等待时间，尤其不能代替真实 WSL 编辑器验收。

## 最近查询的空闲预热

持久化结果现在附带经过完整性校验的查询提示。重载后再次打开相同源码，若缓冲区内容与该提示对应的源码哈希一致，语言服务器在 1.5 秒空闲后静默准备最近的一个候选查询；完成后再准备 Symfony 容器和路由。References 与正在进行的同键候选扫描共用任务，取消或文件变化会使任务失效。背景准备不创建 VS Code 的索引进度通知；它提前消耗计算时间，并未减少首次空缓存的总工作量。

Winstar 的 `get` 样本在已有同版本缓存、打开文件后空闲 8 秒的独立进程中，后台候选恢复约 2.97 秒并完成框架准备，第一次点击 References 为 **1,636 ms**、112 处且位置哈希不变。点击发生在候选预热中途的 2.5 秒空闲场景只出现一次候选扫描，点击用时 5,337 ms；无匹配缓存的点击仍约 9 秒。聚焦 LSP 5 项、结果存储 3 项、构建及 ESLint 通过。以上均为 WSL 文件系统上的 LSP 基准，不是 VS Code Extension Host 实际交互验收；冷首次查询依旧不达标，Goal 继续。

同样保存服务类查询的安全提示，用于下次打开文件时预热候选和框架；其完整结果仍不做点击时的昂贵快照恢复。`AdminSecuritySubscriber` 的独立空缓存首次查询为 5,093 ms / 2 处，写入完成后重载并空闲 8 秒，首次点击为 **971 ms** / 2 处，位置哈希 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd` 不变。此数字依赖既有提示和足够的空闲准备时间，不能代表首次打开新项目时的速度。

## 光标符号的空闲预热

为首次打开、尚无历史查询提示的项目，扩展在活动 PHP 编辑器的光标位置稳定 300 ms 后把文件版本和位置发给语言服务器。语言服务器只对能够精确识别的一个项目符号生成查询提示，继续等待 1.5 秒空闲，再准备对应名字的候选文件与 Symfony 事实。光标移动、文件编辑或查询开始会使过期任务失效；背景任务不显示索引进度。文件打开与内容变化事件可能同时到达，服务器保留最新选择并避免较早的打开流程覆盖它。

Winstar 只读样本、独立空缓存、打开后空闲 8 秒、Symfony Provider 的双场景基准：`get` 首次点击 3,050 ms / 112 处，`AdminSecuritySubscriber` 972 ms / 2 处；位置 SHA-256 分别仍为 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2` 和 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`。另一次 `get` 为 2,417 ms；波动主要取决于点击时 Symfony 准备是否已结束。可用 `PHP_COMPANION_BENCHMARK_SELECTION_PREWARM=1 PHP_COMPANION_BENCHMARK_DOCUMENT_IDLE_MS=8000 node scripts/benchmark-reference-suite.mjs /var/www/php/8.5/winstar2024` 复测。这个优化把工作移到点击前，首次打开到可交互的总计算时间并未缩短；用户打开后立即点击仍走原有约 9 秒的精确查询路径。

最后一次构建后的复测为 `get` 2,673 ms / 112 处、服务类 946 ms / 2 处，SHA-256 均未变化。聚焦 LSP 5 项、TypeScript 类型检查、ESLint 和构建通过；尚未在真实 WSL VS Code Extension Host 验证光标空闲与点击行为。

## 点击发生在预热中途

活动编辑器选中符号的服务器端等待由 1.5 秒缩至 250 毫秒；客户端仍等待光标稳定 300 毫秒。基准驱动新增 `PHP_COMPANION_BENCHMARK_SELECTION_DELAY_MS=300`，让光标通知时序接近扩展的真实行为，并输出实际候选扫描次数。打开文件后 2.5 秒点击的两次独立空缓存测量中，`get` 为 6,404 / 6,948 ms（112 处），服务类为 4,466 / 4,262 ms（2 处）；每次只有一次候选扫描，位置哈希与原基线相同。先前 1.5 秒等待且立即发送光标通知的测量分别为 8,188 / 5,802 ms；两组通知时序不同，不能把差值当成严格 A/B 收益。打开后空闲 8 秒再点击为 `get` 2,361 ms、服务类 958 ms。

对立即点击另试过跳过无目标子串文件的 worker 准备，Winstar `get` 9,067 → 9,205 ms、服务类 4,986 → 5,913 ms，已撤回；直接遍历解析出的成员访问事实替代正则筛选，`get` 的语义阶段从 2,088 ms 升至 9,897 ms，亦已撤回。两项试验的完整引用位置哈希均未变化，说明当前热路径仍依赖现有 worker 预取与廉价正则预筛。250 毫秒预热提前消耗 CPU，并未解决打开后立即点击约 9 秒的等待；真实 WSL 编辑器的体感仍需验证。

最新正式 bundle 空缓存立即点击 `get` 为 9,455 ms，候选 4,717 ms、Symfony 路由 814 ms、语义 2,229 ms，112 处位置摘要不变。主线程与四个 worker 的 CPU profile 均显示实际工作，主线程有约 565 个 GC 样本，worker 各有约 3.5–3.7 千个 idle 样本；采样不能把这些数值直接换算为可回收的墙钟时间。将预读上限从 128 临时提高到 256，一组旧/新为 `get` 9,115/8,863 ms、类 5,100/5,326 ms，候选阶段几乎不变；跳过普通符号查询的命名参数摘要，一组旧/新为 `get` 8,862/9,396 ms、类 5,149/5,029 ms。这些差值无稳定双场景收益，两项均已撤回。继续优化立即点击需要改变候选事实准备或语义解析的工作量，而非单纯调大预读窗口或删掉摘要正则。

短循环脚本现在也输出候选扫描的文件与解析数量。原版独立空缓存 `get` 一次为 9,267 ms；2,289 个文件中解析 1,656 个，其中 1,203 个只登记声明，完整解析约 453 个；候选阶段 4,811 ms、语义阶段 1,964 ms，结果仍为相同的 112 处。试验把“完整解析”进一步限制为源码有直接 `->get`/`::get` 成员语法的文件，成对原版/试验版为 8,798/8,848 ms，候选阶段 4,545/4,604 ms，位置摘要不变，因此撤回。复核实现后确认，声明快照保留源码，查询另一符号时可按需加载方法体；先前关于缓存会直接漏掉另一符号的担忧不成立。后续优化应首先避免对大量候选文件做不必要的扫描或提供可证明安全的按需声明登记；仅把已匹配文件从完整解析改成声明解析，在此语料未缩短关键路径。

再做一次只解析含精确 `get`/`dispatch` 标识符文件的探索试验：解析数从 1,656 降至 453，候选阶段约 3,749 ms，首次完整请求约 7,668 ms，但结果只剩 66 处，位置摘要变为 `99eeb63176b80a8e54b2610e6e8ffe378c7c5ac5441eda56678b8c2d90b7c00e`。这证明被省略的声明文件对跨文件接收者类型是必需的；该试验立即撤回，不能以较低耗时替代完整的 112 处结果。下一步需要在按需声明登记前建立可验证的依赖闭包和保守回退。

进一步保存两组完整位置并逐项比较：丢失的 46 处只位于 6 个控制器，主要是继承得来的 `$this->request` 成员链。探索性地额外加载 Winstar 的 `AppController` 和 `AdminController` 后恢复到 111 处；再补 `NativeRecordController` 及中间的 `EmailRecordsController` 后恢复 112 处及原位置摘要，单次约 7,694 ms、候选 3,581 ms。该试验使用硬编码的项目类名，仅证明按继承依赖补声明具有潜力；不适合作为产品实现，已撤回。通用版本必须从已匹配源码提取并递归加载父类、接口和 trait，并对无法证明完整的接收者类型保守回退。

在上述只解析精确标识符、补齐四个基类且结果仍为 112 处的试验中，对成员查询增加临时计数，仍有 529 个同名语法位置无法解析为任何成员。因此不能把“存在未解析成员”作为自动触发完整扫描的条件；它在结果完整的语料上也会触发。临时计数、硬编码类型和精确筛选均已撤回并重建 bundle。安全的快速路径需要更强的依赖覆盖证明，或在候选文件集合之外建立一个可复用的声明目录。

继承闭包的粗略规模核查：Winstar 含完整 `get`/`dispatch` 标识符的 453 个 PHP 文件中，按源码行统计约有 1,043 条不同的 `use` 导入（其中 717 条 `App\\` 导入），但直接 `extends` 写法仅约 37 种。这些是文本计数，包含评论或别名歧义，不能当作语义解析后的准确依赖数；它提示只遍历直接父类可能较便宜，而盲目加载全部导入可能抵消收益。另将 Symfony 路由 Provider 从候选扫描之后移到之前并行执行，独立空缓存成对测试：`get` 9,238→9,030 ms，服务类 5,059→5,032 ms，位置摘要均不变；路由原本就和容器工作并行，净收益处于波动范围，试验已撤回。下一步聚焦声明目录和依赖闭包，不继续移动路由任务。

首次登记文件时，旧语义表面必然为空；语义工作区现在直接用新文件的声明与可调用项键建立失效集合，保留编辑已有文件时的完整表面比较。Winstar `get` 两轮独立空缓存成对测量为 9,077→8,800 ms、8,798→8,739 ms，112 处及完整位置摘要均不变；服务类一轮并行测试为 5,217→4,911 ms、2 处不变，但并行负载使该组不适合判断收益。Semantic 291 项、Language Server 232 项（另 1 项既有跳过）、改动文件 ESLint、构建通过。此优化只省去首次登记的重复序列化，不改变 1,656 个候选文件的解析规模；首次 `get` 仍约 9 秒，不能据此认为性能目标完成。

## 通用继承闭包试验（仅测试模式）

已实现不依赖 Winstar 类名的探索路径：从精确命中的候选文件提取类声明，逐层解析其直接父类、接口与 trait，并沿 Composer 映射按需加载声明。若项目命名空间下的依赖无法定位，或存在非 PSR-4 自动加载规则且依赖未解析，则退回原来的完整候选扫描。该路径须同时设置内部 `testMode` 与 `experimentalReferenceClosure` 初始化选项；扩展不向用户开放，正式 References 行为没有切换。短循环脚本可用 `PHP_COMPANION_BENCHMARK_REFERENCE_CLOSURE=1` 运行这个试验。

Winstar 独立空缓存 `get` 试验：精确候选解析 453 个文件，递归加载 80 个声明依赖；唯一未解析的 `PHPUnit\\Framework\\TestCase` 属于依赖包。首次查询约 7.6–8.0 秒，仍返回 112 处，位置摘要保持 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2`。无试验标志的正式路径仍解析约 1,656 个候选文件，一次空缓存测得 8,676 ms 和同一位置摘要。单次时间差只有约一秒，尚未达到满意的交互速度。

完成构建和全套测试后再次串行复测：默认路径 8,106 ms、实验路径 7,128 ms；两者各做一次空缓存扫描，分别解析 1,656/453 个文件，结果仍为相同的 112 处及完整位置摘要。Semantic 292 项、Language Server 233 项（另 1 项跳过）、改动文件 ESLint 与构建通过。该对测量支持约一秒量级的潜在收益，但仍只是单次样本。

为缩短下一轮验证，`benchmark-first-references.mjs` 新增 `PHP_COMPANION_BENCHMARK_COMPARE_REFERENCE_CLOSURE=1`：同一 bundle 串行运行默认和闭包试验，各用独立空缓存，自动核对引用数量与位置摘要。命令为 `PHP_COMPANION_BENCHMARK_COMPARE_REFERENCE_CLOSURE=1 PHP_COMPANION_EXPECTED_REFERENCES_SHA256=bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2 node scripts/benchmark-first-references.mjs /var/www/php/8.5/winstar2024 /var/www/php/8.5/winstar2024/src/Security/AdminPasswordChangeGuard.php get last`。首次运行 7,842/7,264 ms，差值 578 ms，仍为相同的 112 处。这个差值小于各轮环境波动，不作为上线收益承诺。

构造了一个非标准文件名的父类：`Consumer extends Base`，`Base` 的属性为 `Bag`，而 `Base` 声明在 `Legacy.php`。仅按精确 `get` 过滤时会漏掉 `Base` 并返回 0 处；新增回退后恢复为 1 处，完整位置摘要与正式扫描一致，并有 stdio 回归测试。这个例子证明回退必要，但不足以证明任意 Composer 项目的精确路径完整；尤其不能仅凭 PSR-4 解析成功就断言不存在其他动态或混合自动加载来源。正式启用前需要建立声明目录与可验证的覆盖条件，或采用更保守的回退策略，并对多种 Composer 布局及真实工作区做差分测试。

## 长名字源码预筛试验（仅测试模式）

对至少 8 个 ASCII 字符的查询名，实验性地先用本机 `rg` 对 Composer 项目自动加载路径执行不受 ignore 配置限制、包含隐藏文件和符号链接的固定子串搜索，再让原来的候选扫描只读取命中的 PHP 源码。项目文件仍逐一计数并检查大小预算；未命中的文件只有在修改时间与状态变更时间都早于预筛开始前 1 秒时才跳过读取。`rg` 缺失、超时、报错或输出超过预算时自动使用完整扫描。已存在且元数据未变化的候选缓存项保留。该路径须由内部 `testMode` 加 `experimentalRipgrepCandidates` 显式启用，正式扩展未启用，也不要求用户安装 `rg`。

Winstar 空缓存、Symfony Provider 的串行差分：`AdminSecuritySubscriber` 类声明 5,095→3,811 ms，完整 2 处位置摘要均为 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`；反向顺序再测，试验 3,764 ms、默认 5,001 ms。`shouldRedirect` 方法声明 4,721→3,572 ms，完整 1 处位置摘要一致。类名场景中 `rg` 用 82 ms 筛出 31 个文件，候选阶段从 2,614 降至 1,222 ms；方法场景筛出 33 个文件，候选阶段从 2,488 降至 1,232 ms。两场景解析文件数与默认路径一致，说明收益来自避免读取原本也不会加入语义工作区的源码。短名字 `get` 未启用该试验，仍需单独解决其约 8 秒首次等待。`PHP_COMPANION_BENCHMARK_COMPARE_REFERENCE_RG=1` 可在同一 bundle 上串行复测并自动核对位置。

这仍只是受控 WSL 基准。推广到正式路径前，需覆盖不同 Composer 自动加载布局、符号链接、文件变化窗口、缓存重载、`rg` 缺失以及真实 VS Code Extension Host；若无法证明预筛的文件集合完整，应继续走原扫描。即使这些条件通过，类名场景约 3.7 秒也尚未达到理想的首次交互速度，后续要进一步缩短 Symfony Provider 和语义准备时间。

已用清空 `PATH` 的独立进程验证 `rg` 缺失：`AdminSecuritySubscriber` 仍走原候选扫描，4,842 ms、2 处及相同位置摘要。项目索引包 36 项、Language Server 234 项（另 1 项跳过）、改动文件 ESLint 通过。预筛路径会少记录未读取文件的内容哈希，因此现有完整 References 结果的持久化证明不会生成；目前不能直接把这个局部加速默认打开，否则可能让重载后的已证实结果恢复退化。正式化需要为预筛集合建立同等严格的完整性证据或在后台补齐哈希，随后复测冷启动与重载两种场景。

## 短名字与语义阶段反证

临时把源码预筛门槛降至 3 个 ASCII 字符后，Winstar `get` 由 8,136 降到 7,418 ms；预筛跳过 633 个原本不会解析的文件，但语义候选仍是 1,656 个。反向串行测量却为试验 7,768 ms、默认 7,740 ms，候选阶段 4,495/4,441 ms，未复现稳定收益。门槛已恢复为 8，不能用长名字预筛声称解决短名字 `get`。

又试验在初次 PHP 解析时保存每个成员访问的语句起点，期望语义查找时避免重新建语法树。112 个 `get` 引用位置虽未变化，但语义阶段升至 5,667 ms，总耗时 11,565 ms；撤回试验并重建正式 bundle 后恢复为语义 1,806 ms、总耗时 7,831 ms，相同位置摘要。该方案触发了更昂贵的按需解析或查找路径，不能合并。CPU 采样仍显示候选更新、worker 通信、GC 与成员解析分担时间；仅移走语法树构建并不足以推断整体收益。

验证脚本增加 `PHP_COMPANION_BENCHMARK_REVERSE=1`，可在同一命令中先跑试验再跑基线，并在输出中记录运行顺序；不再需要分别手工运行两条命令。以类名预筛复测，试验先行为 3,711 ms、基线后行为 4,842 ms，2 处位置摘要相同。短名字冷查询仍是下一项重点。

## 预筛文件的持久化证据

预筛现在记录每个未读取 PHP 文件在扫描时的大小、修改时间与状态变更时间；写入 References 结果缓存前后再次逐一核对这些元数据，同时完整输入快照仍对 Composer 源码根中的全部 PHP 文件读取内容并计算哈希。证据集合要求每个项目源码恰好属于“已读取且哈希一致”或“预筛跳过且元数据未变”之一；任何缺项、重叠或扫描期间变化都放弃缓存写入。`referenceCandidateEvidenceMatches` 的这一扩展不改变普通完整扫描的校验要求。无匹配的源码仍可能在查询后的持久化阶段被完整快照读取，但这项后台工作不计入用户首次点击等待。

在 Winstar 无 Symfony Provider 的 `shouldRedirect` 样本中，试验性 `rg` 预筛首查 2,197 ms、1 处，后台日志确认 `[reference-cache] stored count=1`；重启语言服务器后返回相同位置，日志为 `restored count=1`，点击等待 2,380 ms。独立 `phpCompanion/testReferenceInputs` 审计返回 `captured=true`、`engineVerified=true`、2,537 个快照文件，候选已读文件 33 个。带 Symfony Provider 的 `AdminSecuritySubscriber` 首查 3,730 ms、2 处，也确认写入结果缓存；重启后的同一请求仍进行了候选扫描并重新写入，说明其框架事实恢复条件尚未满足，不能把“已写入”当作该场景“已快速恢复”。

证据改动后的默认（无实验标志）`get` 冷查询复测为 8,057 ms，候选 4,470 ms、语义 1,969 ms，仍是 112 处及原位置摘要；短名字瓶颈未改变。

## 有界预筛进入 Linux 正式路径

完整文件变化证据已通过单元、Winstar 输入审计与跨进程缓存恢复验证后，Linux 语言服务器默认对至少 8 个 ASCII 字符的普通符号查询尝试 `/usr/bin/rg`。使用绝对系统路径避免从工作区 `PATH` 执行未知程序；缺少该工具、退出异常、超过 1.5 秒或输出过大时自动回到原候选扫描。macOS/Windows 仍走原路径。基准驱动可用 `PHP_COMPANION_BENCHMARK_REFERENCE_RG=0` 强制原路径、`=1` 强制试验路径，以便差分；普通启动不传该内部初始化选项。

正式路径在 Winstar、Symfony Provider、`AdminSecuritySubscriber` 类声明空缓存首次查询测得 4,162 ms、2 处，完整位置摘要仍为 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`，候选 1,337 ms，其中 `rg` 104 ms、筛出 31 个文件。已有 stdio 用例扩展为“磁盘文件不含类名、未保存缓冲区新增类引用”，仍返回磁盘与缓冲区中的完整引用。此优化尚未发布成新版 VSIX，也未在用户当前 WSL Alpha Profile 验证。它改善长名字，短名字 `get` 仍沿完整扫描，不满足最终目标。

正式路径改动后的完整 Language Server 测试为 235 项通过、1 项跳过；ESLint、TypeScript 构建通过。`get` 空缓存复测 7,781 ms、112 处，候选 4,450 ms、语义 1,850 ms，无 `rg` 预筛日志，位置摘要仍为 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2`。

## 短名字冷查询的剩余关键路径

继续以独立空缓存和正式 bundle 测量 `get`：一次 8,042 ms，候选扫描 4,550 ms、语义引用 2,001 ms；重复采样的总时长约 7.8–8.1 秒，112 处位置摘要保持不变。临时阶段埋点显示，“打开文件后立即点击”的语义工作区初始化约 816 ms，磁盘结果恢复尝试约 347 ms，目标解析至候选扫描前约 180 ms，候选扫描 4,481 ms，语义引用 1,805 ms。阶段埋点已经撤回；这些数值是单机诊断样本，不应当相加作为稳定性能承诺。

把磁盘结果是否存在的检查移到引擎身份校验之前，首次仍为 8,096 ms；该试验已撤回。完全不配置候选缓存的两次首次查询为 7,011/7,147 ms，候选扫描 3,855/3,953 ms，结果仍为相同 112 处。缓存写入占约 0.6–0.9 秒，但即使牺牲这项重载能力，首次仍约 7 秒，不能作为主要修复。CPU profile 中候选 worker 有大量空闲样本；此前增加 worker 数量没有稳定收益。`src/` 内约 300 个 PHP 文件含直接 `->get` 或 `::get` 文本，与 1,656 个准备候选不同；语义阶段仍必须逐个证明接收者和成员身份，不能用文本位置代替引用结果。

下一轮实现应先针对有界候选准备与成员解析做共享、可取消的工作单元：查询、光标预热和后台准备复用同一批解析事实；编辑或 Composer 映射变化时失效；任何无法证明完整的声明或依赖仍走保守路径。验证只先跑 `get` 的一次空缓存完整位置哈希和阶段耗时，见到超过环境波动的收益后再做反向顺序 A/B、类名与提升属性样本、持久化重启、取消/编辑失效及 Extension Host。当前首查约 8 秒，性能 Goal 仍未完成。

又在仅测试模式把精确 token 的 `rg` 预筛与现有继承闭包组合：`rg` 61 ms 命中 453 个文件，候选阶段 3,303 ms、首次总计 6,804 ms，仍返回 112 处和相同位置摘要。这比单独的闭包试验仅进一步节省约数百毫秒，且闭包路径仍未证明任意 Composer 布局的完整性；试验已撤回，不进入正式扩展。

## 把工作区基础事实移到初始化阶段

临时分段埋点确认，文件刚打开就立即请求 References 时，首个 `semanticForUri` 需要约 0.8 秒建立工作区及 PHP 内置声明。只提前加载解析器没有缩短点击等待；改为在语言服务器 `initialize` 返回前为每个已知工作区建立内置语义工作区。正式 bundle 的两组独立空缓存交叉对照中，`get` 的点击耗时由 7,635/7,683 ms 降至 6,831/7,075 ms；112 个完整位置与原 SHA-256 不变。初始化本身由约 190 ms 增至 1,023–1,067 ms，因此这只是把约 0.6–0.9 秒的基础工作移到扩展启动期，不是减少总 CPU 工作或解决约 4.4 秒的候选扫描。

带 Symfony Provider 的 `AdminSecuritySubscriber` 类首次 References 同轮从 3,787 ms 降至 2,866 ms，均为 2 处、位置摘要 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`。另测带 Symfony Provider 的 `get`：8,773→8,092 ms，仍为原 112 处。短循环脚本现在同时输出 `initializeMs`，避免只报告点击时间而隐藏启动代价。语言服务器 235 项通过、1 项跳过，Core Only 和打包 Core + Symfony 的隔离 VS Code 1.138.0 宿主均 exit 0；一次元数据变化测试在等长内容快速覆写下失败，已改为不同长度的内容，完整套件重跑通过。用户现有 Alpha Profile 未安装这一试验版；总初始化加首查耗时没有净减少，约 8 秒的 Symfony `get` 仍需继续优化。

## 候选缓存写入是否阻塞首查

试验让候选缓存的语义快照压缩和文件提交延迟到 References 返回之后；新的查询在相同项目写入完成前等待，以避免旧快照覆盖新快照，关闭语言服务器时也等待提交。Winstar `get` 的两组空缓存正反顺序对照均保持 112 处和原位置摘要：旧版/试验版为 7,144/7,081 ms、6,997/6,812 ms，候选阶段约少 0.2 秒。收益处于机器波动范围，且延迟任务增加写入顺序和关闭处理的复杂度；代码已撤回，工作树仍使用同步提交。此前完全关闭缓存也只把首查降到约 7 秒。这些数据排除缓存写盘作为数秒级首查瓶颈，后续集中减少 2,289 个候选文件的检查和 1,656 个候选语义准备，同时保持继承、非标准 Composer 布局和开放缓冲区的完整引用结果。

## Symfony 结果缓存的重载阻断点

同一 Winstar/Symfony 工作区连续启动正式 bundle 查询 `AdminSecuritySubscriber`：首次约 2.73 秒，确认 `[reference-cache] stored count=2`；重启后约 2.81 秒，仍重新扫描 2,289 个文件并运行服务/事件 Provider，随后再次写入相同两处结果。持久结果并未加快该重载首查。代码明确要求首次恢复时已有框架指纹，而框架指纹依赖 Provider 事实；这些事实目前在候选扫描和 Provider 执行后才形成。类查询的扫描后恢复又因语义查找本身只需数毫秒而被跳过，因此“已写入”不能推断“下次会恢复”。

诊断中还发现，直接调用 `benchmark-language-queries.mjs` 而不显式传入正式 bundle 时，驱动运行的是未带解析器 WASM 参数的包内入口，无法建立持久证明所需的引擎身份。新增启动参数检查：启用持久化或输入审计时必须指定 bundle 路径，避免把这种无效运行误判为产品缓存失败。恢复带 Symfony 的结果前，仍需为服务、事件、路由 Provider 的程序版本、读取的 PHP/YAML/XML、目录枚举、缺失候选及打开的未保存缓冲区建立完整可验证输入证据；当前外部 Provider 可在项目根目录自行读取文件，不能仅凭已保存的位置和摘要跳过它们。短名字真正首次冷查询仍需独立优化。

## 原有结果摘要不是正确性基线

进一步核对同一 `ParameterBag::get` 查询，发现 `src/Bridge/ApplicationContextSubscriber.php` 的 `publishAdminLanguage()` 中两处直接参数调用被计入，但 `isApplicationRequest()` 中的两处 `$request->attributes->get(...)` 未计入。后者的 `$request` 来自 `$event->getRequest()`；参数 `RequestEvent` 继承 `KernelEvent`，`getRequest(): Request` 实际定义在父类，`Request::$attributes` 的类型为 `ParameterBag`。这是真实引用漏报，不能把原先 112 处和摘要 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2` 当成完整性证明。

只在一次临时诊断运行中加载 `RequestEvent`、`KernelEvent`、`Request`、`ParameterBag` 四个声明后，该局部调用链可以解析，结果由 112 增至 119 处，位置摘要为 `c3c7840bfe35831179a26ae44681ff77ca48c45d1e63162224ff2b670baea662`，首次查询约 6.36 秒（不含 Symfony Provider）。这 119 处仍不代表全部真实引用已经找齐。仅加载 `RequestEvent`、`Request`、`ParameterBag` 时结果仍为 112，说明缺失的父类 `KernelEvent` 是该实例的直接阻断点。

另一个临时试验遍历所有候选成员访问所在函数的参数类型，得到 162 个未加载的候选类型，但额外的作用域/类型查询把一次首查增至约 14.8 秒，且没有补上引用；代码已撤回。后续修复应只对未解析的具体接收者追溯其赋值来源，并按需加载该类型的继承链和成员返回类型。短循环先固定两处 `isApplicationRequest()` 真实调用必须出现，再检查完整位置集合、冷查询分段耗时和取消/编辑失效。任何提速不能继续以原 112 处摘要作为唯一通过条件。

进一步缩到“接收者局部变量由方法调用赋值，且赋值源是当前函数参数”的静态候选，确实只得到 5 个未加载类型（4 个 Symfony Event 类型和 `Aws\S3\S3Client`），包含所需 `RequestEvent`。但现有 `SemanticWorkspace` 按成员键列举候选文件时仍遍历了约 1,600 个工作区文件和约 78,000 个成员访问事实；这次只读预筛自身稳定耗时约 7.7–7.9 秒，首查总计约 15 秒，且尚未加载依赖或补回引用。细分埋点显示词法提取、作用域、赋值及类型查找只占个位数毫秒，余量在候选事实枚举/延迟加载路径。试验已撤回；不能把 5 个类型的较小结果集误认为低成本方案。下一次实现须直接在候选准备阶段生成可复用的接收者依赖摘要，避免查询时再遍历全部成员事实。

## 候选准备时记录接收者依赖

已在每个匹配文件进入语义工作区时提取“局部变量由参数方法调用赋值”的接收者/方法对，并随候选缓存保存；重载直接恢复该摘要，避免查询后再次遍历 78,000 个成员事实。References 查询在语义匹配前只对这些实际候选加载接收者类型、继承链和方法的原生返回类型。Winstar `ParameterBag::get` 查询由 112 增至 127 处，新增 15 处均在 Symfony Event 获取 Request 后访问 `attributes->get()` 的位置；`ApplicationContextSubscriber.php` 原漏报的两处已列入基准脚本的显式断言。新摘要 `64da8a3d32297acd6ff06ec6e25ba54a940f2f81032f9936b85c238622aec531` 只固定当前语料结果，并不证明所有可能的引用都已找齐。

独立空缓存、正式 bundle 的一次冷查询：无 Symfony Provider 约 7.35 秒，有 Provider 约 8.18 秒；有 Provider 的服务类样本约 3.02 秒、原 2 处位置摘要不变。同一缓存目录重载后、禁用 Symfony Provider 的 `get` 查询约 1.68 秒，确认直接恢复已验证的 127 处结果而没有候选重扫。选中符号并空闲 10 秒后点击，带 Symfony Provider 的 `get` 为约 2.45 秒，仍执行约 2.08 秒语义阶段；此前工作移至点击前的效果与总 CPU 时间须分开描述。临时跳过语法树解析会使语义阶段由约 2 秒升至约 5.9 秒，短窗口加失败回退仍约 2.6 秒，均已撤回。立即点击的约 8 秒仍未达到性能 Goal。

## 在已选符号的空闲期完成语义引用

分段计时确认，127 处查询的语义阶段约 1.97 秒，其中 394 个临时语法树约 0.85 秒、1,271 次成员解析约 1.00 秒。试验在候选准备时保存成员语句起点，几乎消除了临时树（3 棵、约 24 ms），但成员解析增至约 5.11 秒，查询总计约 10.45 秒；原因是其他流分析同样依赖已保留的树，试验已撤回，不能把树建立时间直接当作可回收收益。

活动 PHP 编辑器选中一个项目级方法符号后，现有可取消的候选/框架预热完成时，再为该确切光标位置计算一次语义 References，并同时缓存包含声明与排除声明两种结果。查询或文件编辑仍按已有失效机制取消/清理预热。Winstar 只读样本、正式 bundle、空缓存、模拟扩展的 300 ms 光标通知延迟：选中后空闲 8 秒再点击，带 Symfony Provider 的 `get` 首次点击约 0.57 秒、127 处；请求包含声明时约 0.54 秒、128 处。等待 2.5 秒时点击仍约 6.3 秒，立即点击仍约 8 秒。这里改善的是用户已停在符号上的点击等待，不是从打开文件到结果的总耗时；后台同步语义计算约 2 秒仍需继续减小或分片，避免与编辑交错时阻塞语言服务器。包含声明的预热和跨进程结果缓存已在聚焦 stdio 用例验证。

本轮语义包 294 项、语言服务器 236 项通过（另 1 项跳过），改动文件 ESLint 通过；另以正式 bundle 启用原本跳过的跨进程 stdio 用例，验证包含声明的预热。VS Code 1.138.0 隔离 Core Only 和打包 Core + Symfony 扩展宿主均 exit 0。打包测试生成了本地 VSIX，但未安装到用户现有 WSL Alpha Profile；自动化宿主与真实持续编码验收仍是不同证据。

随后临时把 Linux 上的 ripgrep 候选预筛下限从 8 字符放宽到 3 字符。对 `get`/`dispatch` 的一次同 bundle、独立空缓存顺序对照：关闭预筛 8.07 秒，开启预筛 7.94 秒；预筛自身约 48 ms，候选阶段 4.56 秒降至 4.30 秒，结果仍为 127 处且位置摘要相同。但语言服务器全套回归出现 3 处失败：外部新文件证据的候选源数量减少，以及重载时预期缓存恢复数量减少。即便这些是证据数量断言而非位置结果错误，0.14 秒单次收益也不足以支持放宽规则；该试验已撤回，保留原 8 字符门槛。

## 直接参数接收者的冷查询完整性

再次核对精确候选闭包：Winstar `get` 的独立空缓存顺序对照为正式路径 9.37 秒、实验路径 8.08 秒，均为 127 处及相同位置摘要；实验路径只解析 453 个精确命中文件。但构造纯 PSR-4 反例后发现，`Use.php` 中 `run(Consumer $receiver) { $receiver->get(); }`，`Consumer.php` 仅声明 `Consumer extends Bag`，而 `Bag.php` 声明 `get()` 时，`Consumer.php` 没有 `get` 字样：实验闭包无法发现该类。即便在 `Consumer.php` 注释中加入 `target` 使普通宽扫描加载它，正式路径返回 1 处而实验路径返回 0 处。不能因为 Winstar 样本位置相同就把精确闭包推广到正式路径。

同一反例揭示正式宽扫描也会漏报：没有该无关注释时，它同样无法加载 `Consumer`，返回 0 处。现对每个已解析的候选，在提取“参数方法赋值”接收者摘要时也记录直接声明类型的参数接收者；查询前按 Composer 映射加载其类与继承链。候选缓存版本升至 v6，避免旧摘要在重载时漏掉此依赖。聚焦 stdio 测试覆盖首次冷查询与跨进程重载，均返回 1 处；语义提取测试覆盖类尚未加载和已加载两种状态。Winstar 正式 bundle 复测 `get` 为 8.47 秒、127 处及原位置摘要，服务类为 3.16 秒、2 处及原位置摘要。选中 `get` 后空闲 8 秒的点击约 0.80 秒、127 处；这一结果只代表预热后响应。Semantic 全套 295 项、Language Server 全套 237 项通过（另 1 项跳过）；最终缓存版本调整后，重新构建并通过聚焦的冷启动/重载测试。此改动修正正确性，没有解决约 8 秒的冷首查。

试验把候选 worker 上限由 4 提高到 8，Winstar 首查约 8.26 秒、候选阶段 4.68 秒，未见收益，已撤回。下一步若继续缩短空缓存总时间，须处理候选语义准备与成员匹配的实质工作量，同时为任何收窄路径提供对直接参数、继承、动态及 Composer 布局的完整性证明。

反向把 worker 上限降到 2 后，Winstar 相同 127 处查询约 10.79 秒，候选阶段 6.76 秒；恢复 4 个 worker 并重建正式 bundle。与 8 个 worker 的试验共同说明，此样本的主要瓶颈不是线程池配置。继续调 worker 数量会增加验证时间，却不能解决必须解析 1,656 个候选文件和逐个验证成员身份的工作量。

## 隔离 VS Code 扩展宿主测量

从提交 `787b56f` 生成 `artifacts/php-companion-alpha-0.4.5-787b56f8/`，四个 VSIX 通过打包检查和 `SHA256SUMS`，只读 WSL/PHP 8.5 预检通过。严格编辑器预检从当前非 VS Code 集成终端执行时失败：`code` 探测超时，且无法确认 Alpha Profile 中恰好安装一个扩展包；它不代表候选 VSIX 失败。隔离 VS Code 1.138.0 Core + Symfony 打包扩展宿主测试 exit 0，未替代用户实际 WSL Remote Profile 验收。

新增 `pnpm benchmark:references:vscode -- <winstar-root> <alpha-candidate-dir> [idle-ms]`。它用隔离配置文件、仅启用候选 Core + Symfony VSIX，在只读 Winstar 工作区等待 PHP Document Symbol Provider 就绪后，调用 VS Code 标准 `vscode.executeReferenceProvider`；明确核对包含声明的 128 个位置、位置摘要 `a59c441cf79b1a218d5d6375b695bfc64c0e47e3f58326a94b4f797ec92009d6` 和 `ApplicationContextSubscriber.php` 两处继承接收者调用。独立空配置文件各运行一次：`idle-ms=0` 的点击等待 **8,496 ms**，`2500` 时 **5,905 ms**，`8000` 时 **344 ms**，三次均为 128 处。就绪等待分别为约 1.02、0.87、0.83 秒，单独记录，未计入点击耗时。最终带完整位置摘要断言的 8 秒空闲复跑约 463 ms；新 npm 命令的零空闲复跑约 8,169 ms。该测量验证了扩展宿主链路中的预热效果，也确认立即点击仍不达标；隔离 Linux 宿主不是用户的 WSL Remote Alpha Profile，也没有完成持续实际编码验收。

## 收紧首次引用验证循环

改进现有的 `pnpm check:references:winstar`：直接运行正式 bundle，不重新构建整套 monorepo；每次使用独立空缓存，默认启用 Symfony Provider，查询 `AdminPasswordChangeGuard.php` 最后一个 `get`，并断言排除声明的 127 个引用位置摘要为 `64da8a3d32297acd6ff06ec6e25ba54a940f2f81032f9936b85c238622aec531`。输出同时给出候选扫描、容器、路由、事件和语义阶段耗时；需要对照 Core-only 路径时可设 `PHP_COMPANION_CHECK_REFERENCE_SYMFONY=0`。若 Winstar 工作树变化导致摘要不符，先审查位置差异并更新基线，不能直接放宽断言。源码改动时先构建受影响包及 `node esbuild.mjs --production`，再执行该短循环；只有明确超过单机波动且位置完全一致时，才扩大到继承/Composer 反例、包测试和隔离 Extension Host。

本轮同机重测：关闭候选缓存的 `get` 为 7.59 秒，正式缓存路径约 8.25 秒；已有 ripgrep 试验开关的相同 bundle 正反比较为 8.25/8.19 秒，均返回相同 127 处。尝试把缓存提交移出请求关键路径，首次为 8.35 秒；把每个文件的相邻 PHPDoc 查找改为一次排序与二分，独立复跑为 8.09 秒。两项都没有稳定、足以抵消复杂度的收益，产品代码已撤回。CPU 采样显示主线程在候选事实接收和语义成员匹配时仍有大量工作，而候选 worker 在一段时间内空闲；下一个优化应减少主线程逐文件的声明增强/引用核对成本，或者建立能够证明完整性的跨文件依赖索引。不能再把线程数、短词 ripgrep 或缓存写盘当作主要方向。性能 Goal 保持未完成。

重启门禁暴露出一个过时假设：Symfony 组合下恢复已验证的 References 结果之前，仍需恢复候选声明与框架输入以证明结果未过期。一次重启查询约 5.79 秒，候选阶段 2.78 秒、2,288/2,289 个文件由缓存处理、只重解析当前打开的文件，最后日志明确为 `[reference-cache] restored count=127`；原门禁因看到候选扫描就误报。门禁现改为要求缓存结果恢复，并允许这次以缓存为主的证据扫描；若大量候选重建则仍失败。该事实也说明跨进程缓存尚未让重启后的第一次点击足够快。

在相同正式 bundle 上重新比较仅测试模式的精确候选闭包：宽扫描/精确路径为 8.196/7.232 秒，均返回完全相同的 127 处；精确路径只全量解析 453 个文件，候选阶段仍耗 3.749 秒。新增聚焦 stdio 回归，证明它能处理 `Use.php` 的 `Consumer $receiver->get()`，即使 `Consumer.php` 本身完全不含 `get` 且须经 PSR-4 加载继承链。此单例通过不等于各种动态、别名和非标准 Composer 布局的完整性证明；精确模式继续只供测试，不进入正式路径。

临时对正式宽扫描的主线程逐文件处理分段计时，独立空缓存样本总计 7.794 秒、候选阶段 4.207 秒、位置摘要不变。2,289 个文件的 `onSource` 累计约 1.139 秒：语义事实更新 0.751 秒、快照生成 0.305 秒、接收者摘要 0.026 秒；剩余约 3.1 秒在目录/文件读取、worker 准备和最终缓存提交路径。埋点已撤回并重建正式 bundle。单纯优化相邻 PHPDoc 或主线程更新无法独自解决 8 秒首查；后续实验应能减少需解析的文件数量，同时在无法证明类型/继承闭包完整时保守回退。

再以临时埋点统计 `get` 的成员候选：精确候选模式核对 1,277 处访问，其中 514 处 `memberAt` 尚无法确定归属；宽扫描核对 1,271 处，仍有 509 处无法确定。两次最终都返回相同的 127 处目标引用，但这种大量未解析访问说明“当前项目结果相同”不足以证明精确筛选在别的项目也完整。两条路径的实际首次等待分别约 7.10/7.39 秒；埋点已撤回。后续若缩窄候选，必须有可验证的接收者类型依赖证据或对无法判定的路径回退，不能仅凭词法命中集合。

逐位置差分进一步确认两种模式的语义状态并不相同：精确模式额外有 6 处 vendor `get` 调用无法解析，宽扫描额外有 1 处 `AdminController.php` 调用无法解析；若干调用的候选接收者类型也不同。即使这个目标方法的最终 127 处位置暂时一致，也不能把试验路径等同于正式路径。为避免落入“快但漏报”的目标偏移，精确模式继续隔离，不依据当前样本推广。

尝试让现有 experimental 全项目索引只处理项目源、后台空闲 30 秒后查询。索引总共约 33 秒；References 点击约 3.2 秒，但只返回 112 处，漏掉正式路径中的 15 处 vendor 接收者引用，故该预索引方案不能上线。实验开关已撤回。保留一项正确性修复：当 experimental 项目源已就绪而依赖索引尚不完整时，References 仍执行按名字的候选扫描及接收者声明加载，不把“项目文件已索引”误当作“引用类型闭包完整”。同一人为限制依赖索引的 Winstar 样本恢复为完整 127 处及原位置摘要，点击约 8.0 秒。此修复防漏报，并未改善耗时；要让后台索引真正加速，必须同时完成或证明 vendor 接收者依赖，且消除查询时重复扫描。

## 后台预解析原型与下一道门禁

正式 bundle、独立空缓存的 Winstar `get` 首次 References 再测为 8,228 ms、127 处，完整位置摘要仍为 `64da8a3d32297acd6ff06ec6e25ba54a940f2f81032f9936b85c238622aec531`。候选扫描 4,444 ms（2,289 文件，解析 1,656 个候选），容器 805 ms，路由 818 ms，事件 32 ms，语义匹配 2,111 ms；初始化另需 999 ms。把候选读取并发从 128 降到 64 的独立空缓存试验反而为 8,665 ms、候选 4,862 ms，已撤回。此时继续调线程数或读取并发没有证据支持。

为避免首次点击重复做所有准备，临时试验了“后台只索引项目源、worker 预解析、查询时补齐实际 vendor 接收者类型”。无持久缓存时，项目源在约 15 秒内就绪，随后点击约 3.8 秒，并恢复完整 127 处及相同摘要；不使用 worker 的项目源准备约 33 秒。启用持久缓存后，首次后台索引一次为 23.7 秒，重启恢复约 14.1 秒；后续点击约 3.7–3.8 秒。另一次空闲 15 秒点击约 3.37 秒，但 Symfony 服务 Provider 在结果返回后才提交，说明项目源就绪信号与框架事实就绪之间存在竞态。这组速度只说明预解析有潜力，**原型代码已撤回，没有进入正式路径**。

下一步应实现按索引代次跟踪的引用就绪状态：项目源、查询所需的 vendor 接收者声明、Doctrine 与 Symfony Provider 各自完成后，才能跳过对应候选扫描或复用结果。用户立即点击时必须与后台工作共享同一准备任务，尚未就绪的依赖继续走完整保守路径；编辑、Composer 映射变化、取消及缓存恢复都要使状态失效。先用现有 `pnpm check:references:winstar` 在正式 bundle 上核对 127 处及完整摘要，再做正反顺序冷缓存对照、重启/编辑回归，最后测隔离 Extension Host 和用户的 WSL Alpha Profile。只有首查或常见空闲后点击的等待稳定下降，且没有漏报，才推广到默认模式。当前性能 Goal 未完成。

随后的正式 bundle 实验把 experimental 后台全量解析移到 worker，初始化后空闲 15 秒，项目源已经就绪，但依赖索引仍因预算截断（索引合计 2,368 文件，`complete=false`），首次 References 仍需重新扫描 2,289 个项目文件，点击 8,015 ms、127 处、位置摘要不变。worker 改动已撤回；这证明直接加速现有全量索引不能让大型工作区首查复用结果，所需的是按引用查询加载实际依赖、并可与点击共享的准备任务。

另外修正了一项就绪竞态：`completeRoots` 现在要等语义 Provider 提交、可调用事实加载之后才宣告完整；项目源完成不再等于引用事实完整。聚焦 stdio 回归让 Provider 延迟返回，在此期间发起 References，确认执行候选补扫并返回真实引用。默认按需索引的 Winstar 冷首查复测 8,037 ms、原 127 处及摘要，候选 4,433 ms、语义 1,963 ms。语言服务器全套 239 项通过、1 项跳过，改动文件 ESLint 和正式 bundle 构建通过。此修复保障后续后台提速的准确性，但尚未降低冷首查耗时。

## 打开框架配置文件时恢复选中符号预热

发现 `scheduleReferencePrewarm` 把选中符号的内存预热错误地与持久结果复用条件绑定。打开任意 YAML/XML 框架文档后，`frameworkDocumentSnapshots` 非空，持久结果证明按设计停用，但选中符号也不再预热；未配置磁盘缓存时同样被禁用。现仅把“从最近持久结果推断可能查询”留在持久复用门禁内，明确选中的 PHP 符号仍可启动可取消、与首次请求共享的候选准备和语义计算。两个 stdio 回归分别覆盖有/无磁盘缓存且框架快照非空，均只扫描一次并返回准确引用。

正式 bundle、独立空缓存、Symfony Provider、Winstar 实际 `config/symfony/services.yaml` 内容作为打开文档快照的对照：不发送选中预热通知，空闲 8 秒后首次点击 7,703 ms；模拟编辑器延迟 300 ms 发送选中通知，空闲 8 秒后首次点击 **557 ms**。两次均返回 127 处及 `64da8a3d32297acd6ff06ec6e25ba54a940f2f81032f9936b85c238622aec531` 摘要。空闲 2.5 秒时点击仍约 5,594 ms，因为候选准备尚未完成；这再次说明等待从点击前开始，并没有减少总 CPU 工作。基准驱动新增可选 `PHP_COMPANION_BENCHMARK_FRAMEWORK_SNAPSHOT`，以真实磁盘内容复现打开框架文档的条件。刚打开文件立即点击仍约 8 秒，性能 Goal 不应据此关闭。

## 冷首查成本下界复核

对 Winstar Composer 项目源 `src/` 与 `tests/` 的 2,289 个 PHP 文件作只读本机采样：约 9.55 MB 源码生成候选摘要需约 844 ms（单线程）；实际包含 `get` 子串的 1,656 个候选中，453 个完整解析、1,203 个声明解析。单线程依次执行相同解析约 11.3 秒；把同一批文件的语法树构建与事实抽取分开计时，分别约 3.3 秒和 7.3 秒。这些微基准不是正式查询耗时，但说明只换更快的 Tree-sitter 后端不能消除大部分候选准备工作。

临时试验在候选 worker 预读时由主线程预先保留 453 个候选的语法树，语义匹配由约 2.1 秒降至 1.18 秒，但候选阶段由约 4.5 秒升至 5.72 秒，首次总等待为 **8.74 秒**、127 处及原位置摘要。主线程预建树挤占了候选事实提交，无法把同一批 CPU 工作有效重叠；试验已完整撤回并重建正式 bundle。撤回后独立空缓存复测 8.39 秒、127 处及原摘要。下一步应在独立后台任务中构建可复用的项目引用事实，并为查询所需的 vendor 接收者建立可验证依赖闭包；继续在主线程移动或重复语法树解析没有净收益。

## 直接静态调用的免建树试验

对同一 `get` 查询只读统计，1,271 个同名访问中约 459 个是 `Class::get` 这类直接静态访问。试验仅在解析器已记录静态方法访问、且源码紧邻 `Class::` 时跳过该调用的临时语法树；其他访问保持原有解析。正式 bundle、独立空缓存、带 Symfony Provider 的成对测量，旧→新为 8,195/8,298 ms，新→旧为 8,199/8,340 ms；两组完整位置均为相同 127 处与 `64da8a3d32297acd6ff06ec6e25ba54a940f2f81032f9936b85c238622aec531` 摘要，语义阶段分别为旧/新 1,966/1,980 ms 与 2,033/1,943 ms。反向运行未复现净收益，该快捷路径和临时探针已撤回，不增加这项维护面。静态访问与其他访问经常同处一个文件，单个访问免建树并不等于该文件免建树；接下来应优化可复用的文件级引用事实与证明，而不是继续增加单个调用的特例。

## 实验性源索引与选中引用预热

Winstar 工作区现设置 `phpCompanion.indexing.mode=experimental` 和 `phpCompanion.indexing.experimentalSourceOnlyReferences=true`。隔离 VS Code 宿主读取该工作区设置；旧版按需模式的空闲 8 秒点击约 0.4 秒，不能当作当前配置的基线。当前配置下，提交 `00721b1` 的候选空闲 8 秒后仍约 9.6 秒；更早的 `b2694534` 候选同条件约 9.3 秒。宿主日志显示后台项目索引仍在运行，选中符号预热未开始，点击取消索引后重新完成候选扫描。空闲 20 秒后点击约 1.46 秒，说明延长等待能让后台事实就绪，但不能满足常见的短暂停顿。

现在实验性源索引尚未就绪时也接受明确的选中符号预热。预热优先结束未完成的全项目索引，转为与首次 References 查询相同的保守候选扫描；之后仍加载接收者声明、Symfony 事实并计算语义引用。`didOpen` 和 `didChange` 完成后会重新安排当前版本的选中符号预热，避免通知与文档初始化竞态。协议回归覆盖在后台源索引完成前发送选中通知，确认预热与点击共用一次候选扫描，结果为真实引用。

同一 Winstar、同一隔离 VS Code 1.138.0 宿主、当前实验配置、独立空 Profile 的测量：中途候选空闲 8 秒后点击 **78 ms**，最终竞态修正后的重新打包候选为 **658 ms**；两次均有 128 个位置（含声明）和相同的固定完整位置摘要。最终日志中 `[reference-prewarm] semantic count=127` 先于点击出现，点击的语义阶段为 0 ms。刚就绪立即点击仍约 **7,971 ms**，位置摘要一致。这个修复把约 8 秒准备工作从短暂停顿后的点击路径移到选中后的后台；它没有降低完全无空闲时间的总计算量。后续仍须在保持引用完整性的前提下，减少首次候选解析与语义匹配成本。

## 已建源索引后的即时重载查询

验证循环新增 `PHP_COMPANION_CHECK_REFERENCE_RELOAD=1 PHP_COMPANION_BENCHMARK_REFERENCE_SOURCE_ONLY=1 PHP_COMPANION_CHECK_REFERENCE_PRIME_THEN_IMMEDIATE=1 pnpm check:references:winstar`。第一进程等待实验性源索引及框架事实完成并查询；第二进程复用同一缓存目录，在初始化后立即查询，不等待后台索引。两阶段都要求 `get` 的 127 处完整位置摘要和继承接收者两处位置一致。这样单次运行就能检验“用户此前已经完成一次索引，但重载后立即点击”的实际边界，不把预热后的快结果混作冷查询。

当前正式 bundle 的首次源事实准备约 **18.3 秒**、随后点击约 **3.7 秒**；重载后立即点击仍为 **8.46 秒**，重新解析 1,656 个候选（其中 1,203 个仅声明），位置摘要不变。此时源索引缓存虽已存在，但查询取消后台索引，按名称的候选缓存还不存在。查询完成并写入候选缓存后，再次重载点击约 **6.5 秒**：候选恢复 2,288/2,289 个文件需约 2.64 秒，语义匹配仍约 2.31 秒。源索引缓存是约 **126 MB** 的单个 JSON；只读本机试验读取约 1.37 秒、解析约 1.42 秒，进程 RSS 约 502 MB。因此直接在查询中加载整个源索引缓存不能构成低延迟解法；下一步需要按文件或名字读取且带源哈希证明的持久引用事实。

试验把 Symfony 静态路由 Provider 提前到候选扫描期间运行，正式 bundle 冷首查仍约 **8.43 秒**、127 处与原位置摘要一致。路由等待已和容器 Provider 并行，提前运行没有缩短关键路径；试验代码已撤回，避免增加并发失效复杂度。

随后试验按文件压缩保存实验性源索引的完整语义快照，候选查询只在当前源哈希及快照校验通过后恢复，失败则保守解析。它确实恢复了 1,655 个候选事实，127 处位置和完整摘要保持不变；但首次源事实准备由约 18.3 秒升至 **21.45 秒**，重载后立即点击由约 8.4 秒升至 **11.62 秒**，其中按文件读取、解压和校验 1,655 份快照的候选阶段为 **7.96 秒**。该试验已完整撤回并重建正式 bundle。可按文件读取只是存储形式，若查询仍要恢复几乎全部候选，反而更慢。下一个有效方案必须先建立带保守回退的名字和接收者依赖证据，显著减少查询实际读取的文件数；不能把哈希校验或不确定接收者省略掉来换速度。

再次使用同一短循环和 Node CPU 采样查看首次查询：正式 bundle 冷查 **8.99 秒**，候选扫描 **4.85 秒**、容器 **0.80 秒**、语义匹配 **2.40 秒**，127 个位置和固定 SHA-256 均通过。主线程采样可见候选结果接收和解析占用，四个候选 worker 在查询后段有大量空闲。为验证序列化是否造成瓶颈，仅把 worker 返回的 JSON 字符串改成直接 structured clone；同机独立空缓存查询为 **8.80 秒**，候选扫描 **4.79 秒**、容器 **0.89 秒**、语义匹配 **2.13 秒**，位置仍完全相同。差值落在单次运行波动内，不能证明提速；试验代码已撤回。候选并行度或传输格式的微调暂不应成为主要方向，下一步需在保持完整引用集的前提下减少首次查询必须解析的候选，或者减少语义阶段每次成员调用的解析工作。

## 纠正首次引用的完整性基线

重载验证暴露旧 127 处基线并不完整：同一 Winstar、同一符号在全量源事实就绪后返回 **174** 处，额外 47 处中包括 `ApplicationContextSubscriber.php` 的 `$request->server->get('REMOTE_ADDR')`、`Request.php`/`Response.php` 内的 ParameterBag 调用。原候选路径缺少 `ServerBag` 等已加载依赖的接收者继承链，导致真实引用被静默遗漏。两组位置对比为旧结果 127 处全部保留、新增 47 处。仅因结果相同而通过的旧宽/窄候选对照不能证明引用完整。

## 缩短冷查验证循环并定位下一处耗时

新增 `pnpm check:references:fast:winstar`：仅构建语义包和语言服务器、重新打包正式扩展，再执行已有的空缓存 Winstar References 位置门禁。改动索引器、解析器或 Symfony Provider 时，仍需先构建对应包；这一快捷命令只适用于语义包或语言服务器改动，不能替代完整测试或扩展宿主验收。门禁逐次检查排除声明的 **174** 处、完整 SHA-256 `a525dddaa628ccd7ee25dbd5dbfae0ead5e9ebedb434b9176336eb08c1c725e7`、两处继承接收者位置，以及随后 Definition 的结果，并打印候选、容器、路由、事件、语义各阶段耗时。

临时逐项计时测得一次冷查的语义匹配遍历 **1,627** 个文件、匹配 **1,274** 个同名片段，其中 **396** 个文件临时建树耗时约 **1.02 秒**，成员语义判定约 **1.29 秒**；已有成员访问事实覆盖 **1,271** 个片段，所以单靠过滤注释或其他文本误命中几乎无收益。候选加载仍约 **4.3–4.8 秒**，是最大单段。试着省去候选提交时重复计算接收者提示，冷查保持 174 处，相关两项回归通过，但候选阶段的 **4.33/4.44/4.75 秒**处于原先约 4.4–4.7 秒的波动范围，不能证明提速，因此该试验已撤回。跨进程持久结果门禁第一次因未观察到写入而失败，复跑通过：冷查 **9.25 秒**、重载恢复 **5.88 秒**，位置摘要均一致；需要单独追踪写入门禁偶发不稳定，不能把一次复跑当作消除问题。

下一步集中在候选准备的逐文件事实提交与缓存写入，须保持包含继承/vendor 调用的 174 处门禁。先用快捷命令对比正反顺序的独立空缓存样本；只有差值明显超过约数百毫秒的单机波动，才保留优化。之后跑跨进程恢复、延迟 vendor 接收者、隔离扩展宿主；零空闲首次点击仍约 8–9 秒，当前性能 Goal 未完成。

另试验由主线程提前跳过不含查询名字的文件，减少空候选 worker 消息，但候选阶段仍为 **4.59 秒**、冷查 **9.16 秒**，174 处摘要不变，未见收益，已撤回。

## 候选解析成本的可重复测量

新增 `pnpm benchmark:reference-candidates /var/www/php/8.5/winstar2024 get dispatch`。该只读脚本用与正式扫描相同的 Composer 项目路径、候选摘要和解析器，逐项报告候选数、声明/全量解析耗时；修改索引器或解析器后须先构建相应包。它是单线程诊断，不代表语言服务器的并行请求耗时。当前样本扫描 **2,289** 个文件，准备 **1,656** 个候选、约 **8.65 MB**：候选摘要 **0.83 秒**，**1,203** 个声明候选解析 **3.22 秒**，**453** 个完整候选解析 **4.71 秒**，整个诊断约 **12.34 秒**。第二次直接遍历相同候选的样本为摘要 **0.92**、声明 **3.68**、完整 **5.02** 秒。CPU 采样的高频位置包括 Tree-sitter/WASM、`visitNode` 和候选摘要；这是定位线索，不是准确的阶段归因。

这些数据纠正了“只优化 1,203 个声明候选就能解决首查”的判断：即使假设声明解析成本全部消失，单线程仍有约 4.7 秒的完整候选解析，加上约 2.4 秒的语义匹配和框架工作。必须并行推进**跨重载复用已验证的引用结果/项目事实**与**新工作区真正冷启动的候选解析架构**。跨重载快速路径仍须验证 Composer、工作区文件、未保存缓冲区、Provider 代码与运行输入；现有 Symfony Provider 结果依赖项目类型快照，不能在候选加载前简单复用原 `frameworkFingerprint`。新工作区路径仍以 174 处及继承/vendor 位置为准确性门槛。

## 窄候选闭包的返回类型遗漏

比较同一 bundle 的宽/窄候选模式，Winstar `ParameterBag::get` 原先窄模式为 **172** 处，少了 Symfony `Response.php` 第 288 与 1317 行两处调用。追踪发现 `src/Integration/SoFinder/EditorImageSubscriber.php` 的 `$event->getResponse()` 提供了 `ResponseEvent::getResponse(): Response` 接收者线索。窄模式已取得该返回类型，却把一批最多 16 个类型名展开成超过 16 条 PSR-4 候选路径后静默截断；`Response.php` 没有加载。改为给 References 接收者水合设置完整的 64 路径上限，超限时明确失败，不再返回可能不完整的结果。返回类型如果只加载了声明，而源码含目标方法名，也须在引用结果确定前加载实现。独立协议用例用多条 PSR-4 映射和 vendor `Response` 复现旧版的空结果；还原旧截断时测试失败，修正后通过。Winstar 门禁额外逐项确认上述两处 vendor 位置。

窄候选模式仍限于 `testMode`。带 Symfony Provider 的空缓存同 bundle 对照，`get` 正序宽 **8.21 秒**、窄 **7.48 秒**，反序宽 **8.98 秒**、窄 **7.58 秒**；宽模式解析 1,656 个候选，窄模式 453 个，均为相同 174 处和完整位置摘要。另取 `ParameterBag::set` 与 `has`，宽/窄分别为 **7.78/6.50 秒**（74 处）和 **5.62/5.06 秒**（14 处），位置摘要均相同。这证明当前样本中的返回类型阻断已经解决，不证明 PHPDoc、动态接收者、非标准 Composer 布局和未加载依赖在所有项目里完整。正式默认首次点击仍采用宽扫描，约 8–9 秒；继续为窄模式建立失效与缺漏的保守回退证据后，才能把这些样本的提速交给用户。

随后构造了一个独立反例：`Consumer.php` 只有 `/** getter */ class Consumer extends Bag {}`，调用文件通过 `$receiver = new Consumer()` 或 `/** @var Consumer $receiver */ $receiver = factory()` 再调用 `get()`。宽扫描因文件中的 `getter` 字样加载 `Consumer` 的声明，窄扫描最初跳过它，错误地返回零处。候选接收者提示现在从已解析的新建赋值、以及紧邻赋值的单一类名 `@var` 注解提取需水合的类型；注解文本仍不直接成为引用。协议回归覆盖两种形式，窄扫描与宽扫描均返回两处相同位置。这个修正增加了窄模式的覆盖范围，但不能推断任意泛型/联合注解、复杂赋值、运行时类型或非 PSR-4 类也已闭合，因此没有启用默认窄扫描。修正后正式宽扫描复测 **8.37 秒**、174 处和原摘要，候选阶段 **4.46 秒**；这是单次核对，不是新速度承诺。

## 窄扫描的未解析调用与声明候选成本

## 框架输入证明与解析成本上界

检查正式的持久结果恢复条件后，确认带 Symfony Provider 的结果必须等服务/路由/事件事实重算，才能得到用于比对的 `frameworkFingerprint`。服务 Provider 还可读取 `config/bundles.php`、内核、项目及 bundle 内导入的 YAML/XML/PHP 配置，并可采用 `var/cache/dev` 的编译容器 XML；路由 Provider 支持递归/通配符导入。现有持久结果证明以 Composer 源根与语义依赖读集为主，尚不能在 Provider 执行前证明这些目录中没有新增输入。因此不能把“缓存里已有 174 处”直接当作可跳过 Provider 与候选扫描的证据。若做跨重载快恢复，需要 Provider 提供带目录枚举、缺失路径、环境和实现身份的完整输入证据；证据不完整时继续正常重算。

对同一 **1,656** 个候选做只读 CPU 采样，并单独计时两个摘要扫描：约 **8.65 MB** 源码的符号标识符正则 **0.13 秒**、命名参数正则 **0.48 秒**（均为单线程累计）；Tree-sitter/WASM、语法节点访问与解析器 `visitNode` 是更大的 CPU 热点。命名参数扫描即使完全消除，也只能节省不足半秒单线程 CPU，进入四 worker 冷查询后的可回收等待更小；不应为它升级缓存 schema。新工作区冷查的主要方向是减少必须完整解析的文件与每次语义遍历，或以受版本/输入校验的预计算结果避免重复解析。上述采样是诊断，不是速度改进；性能 Goal 保持开放。

## 建树与事实提取的成本拆分

候选剖面现可用 `PHP_COMPANION_PROFILE_TREE_ONLY=1 pnpm benchmark:reference-candidates /var/www/php/8.5/winstar2024 get dispatch` 在正常解析完成后，对同批源码另做只建树诊断，不改变默认脚本耗时。一次采样中，**1,203** 个仅声明候选的完整 `prepare()` 累计 **3.29 秒**、单纯建树 **1.71 秒**；**453** 个完整候选的 `prepare()` 累计 **4.64 秒**、单纯建树 **1.00 秒**。后者约 **3.64 秒**的差额还包含事实提取、树访问与销毁等工作，不能全归为某一个函数；两次遍历有 JIT/缓存顺序效应，数值只用于寻找量级。正式空缓存 LSP 同一轮返回 **174** 处及固定位置摘要，约 **9.22 秒**，候选 **4.72 秒**、语义 **2.29 秒**；采样时的性能不是产品提速。

该冻结样本没有复制 Winstar 的已编译 Symfony 容器。只读复核 `AdminSecuritySubscriber` 类 References 时，样本返回 **1** 处，当前 Winstar 工作树返回 **2** 处及既有类位置摘要 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`。因此样本适用于 `get` 的固定位置对照，不能代替真实工作树的服务/事件关系验收；也不能把样本上的其它类结果视为完整性证明。当前 Winstar 工作树仍有并行编辑，`get` 位置摘要又发生变化，不能静默更新既有硬编码基线。
