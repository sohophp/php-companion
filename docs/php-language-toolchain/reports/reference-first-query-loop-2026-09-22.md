# 首次 References：缩短验证循环与瓶颈复核

本轮以 Winstar 源码为只读样本，查询 `AdminPasswordChangeGuard.php` 最后一个 `get`，启用 Symfony Provider。每次使用正式 bundle、独立空缓存，先发 References，再核对结果数量和排序后的位置 SHA-256。目标是定位首次查询的实际关键路径；此报告不代表 WSL 编辑器交互验收。

新增 `scripts/benchmark-first-references.mjs`，把单次冷查询、阶段日志提取、结果哈希及可选基线对比合成一个命令。候选和基线各使用独立临时缓存；结果数量或位置哈希不同则直接失败。快速迭代先跑单次候选，只有观察到稳定收益时再交叉复测，避免每个猜想都等待四次完整冷启动。

```bash
PHP_COMPANION_BENCHMARK_SYMFONY=1 \
PHP_COMPANION_EXPECTED_REFERENCES_SHA256=bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2 \
node scripts/benchmark-first-references.mjs \
  /var/www/php/8.5/winstar2024 \
  /var/www/php/8.5/winstar2024/src/Security/AdminPasswordChangeGuard.php \
  get last dist/language-server.js
```

同一工具末尾可加基线 bundle 路径，自动对比引用集合。`PHP_COMPANION_BENCHMARK_RSS=1` 可输出进程峰值内存。此命令复用已有 `benchmark-language-queries.mjs` 的 LSP 流程，不绕过真实语言服务器。

当前正式 bundle 的单次测量：首次 References 9,043 ms、112 处，位置哈希 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2`；候选扫描 4,593 ms，容器事实 791 ms，路由 810 ms，事件 37 ms，语义引用 2,085 ms。容器和路由任务有重叠，阶段数值不可直接相加。候选扫描完成后的缓存等待 27 ms，连同写盘约 263 ms，不能解释主要耗时。

本轮对三个低风险假设做了冷查询验证，结果均保持 112 处及相同位置哈希，但没有稳定速度收益，因此未保留产品实现变更：跳过新文件的语义表面比较（旧版 9,016/9,578 ms；试验版 9,040/9,120 ms）；直接使用已解析成员访问事实筛选候选（单轮 9,103 ms，语义阶段 2,344 ms）；候选解析 worker 从 4 增至 6（对比 8,992 → 9,293 ms，候选阶段 4,482 → 4,679 ms）。这些数据表明当前机器上的瓶颈不是单一序列化、文本匹配或 worker 数量。

后续应针对候选准备和语义解析做更细的 CPU/等待分解，再修改算法；保持完整位置哈希、首次冷查询和取消/编辑失效行为作为接受条件。当前首次立即查询仍约 9 秒，未达到满意水平，Goal 继续。

## 后续分段采样

对同一冷查询再做正式 bundle 采样（8,871 ms，112 处及上述哈希不变）：`indexComposerSources` 处理 2,289 个项目文件，目录枚举 273 ms，预取等待合计 608 ms，逐文件应用合计 3,286 ms，缓存提交约 253 ms。另一轮更细的采样中，逐文件应用合计 3,425 ms；其中 `onSource` 1,691 ms，语义工作区更新 974 ms，快照创建 321 ms。计时埋点均已撤回，未加入产品运行路径。

未压缩 bundle 的 CPU profile 显示四个候选解析 worker 在该请求期间大部分样本为空闲，主线程出现 worker 消息反序列化、语义工作区更新和成员解析热点。将 PHPDoc 查找改为范围二分搜索的一次 A/B 测试为 9,248 → 9,232 ms，未达到稳定收益；预先跳过不含目标名字的 worker 任务，两组交叉测量中新版 8,938/9,178 ms、原版 9,055/9,065 ms，也处于波动范围。两项试验均已撤回。

下一阶段重点是减少短名字（例如 `get`）冷查询需要准备的声明文件数量，并在只读项目、包含继承与跨文件接收者类型的语料上核对完整位置集合。单纯增加 worker 或减少缓存写入，按本轮分段数据不足以解决首次约 9 秒的等待。

对同一 `get` 查询加临时声明访问计数后，语义引用阶段进行了 14,296 次 `fileAndDeclaration` 查找，但实际只触及 1,203 个延迟声明文件中的 24 个；首次查询 8,968 ms，112 处及位置哈希不变。埋点已撤回。这支持把延迟声明文件先保留为已准备的事实，按查询实际访问的类型再应用到工作区；实现前必须保证找不到类型时仍能保守回退，且跨文件继承、非 PSR-4 声明、开放编辑缓冲区及缓存恢复都不漏引用。现阶段不能仅凭 24/1,203 的单一语料数据跳过其余声明。

## 浅层声明与查询内缓存试验

实现过一版浅层声明注册：候选扫描时只登记解析器提供的原始声明，实际查到类型时再补齐 PHPDoc 与成员事实；缓存恢复保守地重新解析声明。Winstar `get` 首次查询的候选阶段由基线 4,792 ms 降到 4,295 ms，完整位置集合不变，但事件相关性检查会逐个访问已注册服务类并触发延迟补齐，事件阶段从约 35 ms 升到 1,633 ms，总耗时从 9,235 ms 升到 10,727 ms。加入只排除已证明无继承、接口或 trait 关系的预筛后，事件阶段降到约 0.3 秒；交叉测量仍出现新版 9,460 ms、基线 8,834 ms。该方案未表现出稳定总收益，已撤回。

另试过仅在一次 References 计算中缓存 `fileAndDeclaration` 查找，并在相关文件事实更新时失效；语义阶段约 2,156 ms，对照约 2,189 ms，处于测量波动范围，亦已撤回。两条试验均保持 112 处及相同位置 SHA-256；聚焦的 stdio 测试通过。它们表明延后声明工作和局部查找缓存没有消除关键路径，下一步应评估查询前可复用、有限时且可取消的项目准备，以及点击发生在准备过程中时的实际等待时间。不能把后台提前消耗的 CPU 时间表述为计算量减少。

## 项目预索引和重载成本

Winstar 2,289 个项目 PHP 文件，用现有 `indexComposerSources` 和完整语义更新做一次项目范围预索引，耗时 15,850 ms（不含完整扩展的 Doctrine/Symfony 分析）。把语言服务器直接切到现有 `experimental` 后立即发 References，查询仍为 9,575 ms、112 处；后台索引与按需候选扫描同时运行，未形成可复用的单一路径。未经任务合并与取消设计，不能默认开启完整后台索引，否则可能重新出现长时间“Indexing PHP symbols”。

相同缓存目录连续启动两次 on-demand 语言服务器：第一次 References 9,457 ms，第二次 7,445 ms，位置哈希相同。第二次候选扫描已恢复 1,655 个缓存候选，但仍花 2,947 ms，之后 Symfony 容器约 0.88 秒、语义查找约 2.22 秒。当前持久化的完整 References 结果只对没有语义/路由 Provider 的模式启用；在实际 Symfony 配置下，即使等待持久化任务，重载也不能直接复用完整查询结果。下一阶段若扩展持久化范围，必须先建立 Provider 输入和版本的完整证据校验，不能直接放宽开关。

Provider 输入审查确认 Symfony 服务分析读取项目配置 YAML/XML/PHP、编译容器 XML、Composer 元数据和依赖包配置资源。现有引用输入快照此前只发现目录中的 PHP 文件，无法证明新配置文件未出现。本轮扩展快照的可选文件扩展名选择，并测试 YAML/XML 的新增、修改及选择集变化会改变指纹；默认仍只选 PHP。Winstar `config/` 的 41 个匹配文件做一次完整快照约 37 ms。这个基础设施尚未使带 Symfony Provider 的结果缓存可用：仍需完整记录 Provider 命令/构建身份、所有实际与潜在配置目录、环境选择及其外部依赖，并验证结果缓存恢复时这些证据未变化。

把基准驱动的索引模式切为现有 `experimental` 并在 `initialized` 后等待 20 秒，Winstar 的首次点击仍需 15,407 ms；日志显示查询又启动了 2,289 文件候选扫描（11,575 ms），与尚未完成的完整索引争用资源。`discoverComposerRoots` 在此工作区只发现一个根，不能将延迟归咎于多项目发现。独立的项目 PHP 完整语义索引（不含完整扩展中的 Doctrine/Symfony 分析）为 15,850 ms，因此当前完整后台索引不能直接作为首次 References 加速方案。基准驱动现允许最多 30 秒的可选初始等待，便于把启动准备与点击延迟分开记录。

## 跳过非精确 token 声明的下界试验

基准驱动可用 `PHP_COMPANION_BENCHMARK_REFERENCE_LOCATIONS_PATH` 输出完整 LSP 位置数组，供两版逐项比较。临时试验完全不把 1,203 个只有 `get` 名字片段、没有精确 `get` token 的文件声明加入语义工作区；正式 bundle、空缓存、相同 Symfony Provider 下，首次 References 从基线 9,327 ms 降至 8,057 ms，但 112 处中漏掉 46 处，没有新增误报。漏项集中在依赖其他文件类/继承信息的控制器调用。试验代码已撤回。即使能零成本按需补齐全部必要声明，这一组样本的候选阶段可回收上界也约 1.3 秒，单独做声明延迟加载不足以把首次查询降到满意水平；精度优先，不能直接跳过这些文件。

## 扫描让出频率的验证

将候选索引主线程的让出间隔从每 10 个文件临时改为每 100 个文件，在同一次基线先行的空缓存 A/B 中，基线首次 References 为 8,874 ms、候选为 10,114 ms；候选扫描分别为 4,583 / 5,142 ms。两版都是 112 处，位置哈希相同。该改动已撤回，不能以减少事件循环调度次数代替结构性优化；更低让出频率还会损害取消请求的响应。下一步应把“项目候选准备、Provider 所需项目类型、语义引用查找”设计为可共享的工作单元，避免首次点击在同一批文件上重复准备事实；先以一处短名字查询建立结果集合和取消/编辑失效门槛，再扩展语料。

## 单次查询内的成员组合复用

正式 bundle 的 CPU profile 显示语义查找反复进入 `members()` 组合同一类型的继承及成员事实。现仅在一次同步 References 计算期间复用相同类型、访问作用域、可见性和模板参数的顶层成员列表；查询结束即清空，项目编辑或 Provider 更新不会跨查询复用旧结果。Winstar 同一 `get` 样本的两次空缓存 A/B 中，先跑旧版时语义阶段为 2,246 / 1,875 ms（旧/新），反向顺序为 2,308 / 2,091 ms；完整查询分别为 9,060 / 8,970 ms 和 9,528 / 9,141 ms。两组均为 112 处且位置哈希不变。收益集中于语义阶段，完整查询仍约 9 秒，不能据此称首次等待已解决。Semantic 291 项、聚焦 LSP 4 项、ESLint 和构建通过；尚未完成真实 WSL 编辑器操作验收。

## 双场景短循环

新增 `scripts/benchmark-reference-suite.mjs`，一次检查 Winstar 的短名字方法 `get` 和 Symfony 服务类 `AdminSecuritySubscriber`。每个样本独立空缓存，固定 Symfony Provider，并核对完整位置 SHA-256；可选传入旧 bundle 做结果与耗时 A/B。当前正式 bundle 单次运行分别为 9,023 ms / 112 处和 5,246 ms / 2 处。类查询的候选、容器、事件阶段约为 2.6 / 0.85 / 0.75 秒，语义阶段仅数毫秒；它与短名字方法的约 2 秒语义查找是不同瓶颈。两类工作负载必须分别通过，不能只优化一种。

把扫描并发预取从 128 临时降到 32 后，`get` 查询仍为 112 处且哈希一致，但候选阶段升到 5,929 ms、完整查询 9,994 ms；改动已撤回。后续不再单独降低预取并发，应优先让候选索引和 Provider 输入在首次查询前或查询间复用，并保证查询过程中没有第二个竞争性全项目扫描。

## Symfony 模式的跨进程结果复用

方法引用现在可以在候选扫描及 Symfony Provider 重新计算后，使用持久化的完整结果跳过昂贵的语义引用遍历。写入时记录外部语义事实及框架引用位置的指纹，恢复时要求指纹、引擎身份、Composer 输入、已加载源码与完整文件快照一致；不满足条件便正常重新计算。类查询的语义遍历仅需数毫秒，因此不做这种需要整项目快照的恢复。跨进程测试验证同输入命中，以及新增公开 Symfony 服务配置后拒绝旧结果并重算。

Winstar 的 `get` 样本同一缓存目录连续启动：首次 9,283 ms，第二次 6,553 ms，都是 112 处且位置哈希不变；第二次仍需候选恢复 2,845 ms 和容器/路由约 0.85 秒，快照验证抵消了部分语义遍历收益。新代码的独立空缓存双场景测量为 `get` 9,025 ms / 112 处、`AdminSecuritySubscriber` 5,190 ms / 2 处，位置哈希均不变。缓存尚未达到满意的首次等待时间，尤其不能代替真实 WSL 编辑器验收。

## 最近查询的空闲预热

持久化结果现在附带经过完整性校验的查询提示。重载后再次打开相同源码，若缓冲区内容与该提示对应的源码哈希一致，语言服务器在 1.5 秒空闲后静默准备最近的一个候选查询；完成后再准备 Symfony 容器和路由。References 与正在进行的同键候选扫描共用任务，取消或文件变化会使任务失效。背景准备不创建 VS Code 的索引进度通知；它提前消耗计算时间，并未减少首次空缓存的总工作量。

Winstar 的 `get` 样本在已有同版本缓存、打开文件后空闲 8 秒的独立进程中，后台候选恢复约 2.97 秒并完成框架准备，第一次点击 References 为 **1,636 ms**、112 处且位置哈希不变。点击发生在候选预热中途的 2.5 秒空闲场景只出现一次候选扫描，点击用时 5,337 ms；无匹配缓存的点击仍约 9 秒。聚焦 LSP 5 项、结果存储 3 项、构建及 ESLint 通过。以上均为 WSL 文件系统上的 LSP 基准，不是 VS Code Extension Host 实际交互验收；冷首次查询依旧不达标，Goal 继续。

同样保存服务类查询的安全提示，用于下次打开文件时预热候选和框架；其完整结果仍不做点击时的昂贵快照恢复。`AdminSecuritySubscriber` 的独立空缓存首次查询为 5,093 ms / 2 处，写入完成后重载并空闲 8 秒，首次点击为 **971 ms** / 2 处，位置哈希 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd` 不变。此数字依赖既有提示和足够的空闲准备时间，不能代表首次打开新项目时的速度。

## 光标符号的空闲预热

为首次打开、尚无历史查询提示的项目，扩展在活动 PHP 编辑器的光标位置稳定 300 ms 后把文件版本和位置发给语言服务器。语言服务器只对能够精确识别的一个项目符号生成查询提示，继续等待 1.5 秒空闲，再准备对应名字的候选文件与 Symfony 事实。光标移动、文件编辑或查询开始会使过期任务失效；背景任务不显示索引进度。文件打开与内容变化事件可能同时到达，服务器保留最新选择并避免较早的打开流程覆盖它。

Winstar 只读样本、独立空缓存、打开后空闲 8 秒、Symfony Provider 的双场景基准：`get` 首次点击 3,050 ms / 112 处，`AdminSecuritySubscriber` 972 ms / 2 处；位置 SHA-256 分别仍为 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2` 和 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`。另一次 `get` 为 2,417 ms；波动主要取决于点击时 Symfony 准备是否已结束。可用 `PHP_COMPANION_BENCHMARK_SELECTION_PREWARM=1 PHP_COMPANION_BENCHMARK_DOCUMENT_IDLE_MS=8000 node scripts/benchmark-reference-suite.mjs /var/www/php/8.5/winstar2024` 复测。这个优化把工作移到点击前，首次打开到可交互的总计算时间并未缩短；用户打开后立即点击仍走原有约 9 秒的精确查询路径。

最后一次构建后的复测为 `get` 2,673 ms / 112 处、服务类 946 ms / 2 处，SHA-256 均未变化。聚焦 LSP 5 项、TypeScript 类型检查、ESLint 和构建通过；尚未在真实 WSL VS Code Extension Host 验证光标空闲与点击行为。
