# 首次 References：缩短验证循环与瓶颈复核

本轮以 Winstar 源码为只读样本，查询 `AdminPasswordChangeGuard.php` 最后一个 `get`，启用 Symfony Provider。每次使用正式 bundle、独立空缓存，先发 References，再核对结果数量和排序后的位置 SHA-256。目标是定位首次查询的实际关键路径；此报告不代表 WSL 编辑器交互验收。

新增 `scripts/benchmark-first-references.mjs`，把单次冷查询、阶段日志提取、结果哈希及可选基线对比合成一个命令。候选和基线各使用独立临时缓存；结果数量或位置哈希不同则直接失败。快速迭代先跑单次候选，只有观察到稳定收益时再交叉复测，避免每个猜想都等待四次完整冷启动。

```bash
PHP_COMPANION_BENCHMARK_SYMFONY=1 \
PHP_COMPANION_EXPECTED_REFERENCES_SHA256=bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2 \
node scripts/benchmark-first-references.mjs \
  /var/www/php/8.5/winstar2024 \
  /var/www/php/8.5/winstar2024/src/Security/AdminPasswordChangeGuard.php \
  get last dist/language-server.js
```

同一工具末尾可加基线 bundle 路径，自动对比引用集合。`PHP_COMPANION_BENCHMARK_RSS=1` 可输出进程峰值内存。此命令复用已有 `benchmark-language-queries.mjs` 的 LSP 流程，不绕过真实语言服务器。

当前正式 bundle 的单次测量：首次 References 9,043 ms、112 处，位置哈希 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2`；候选扫描 4,593 ms，容器事实 791 ms，路由 810 ms，事件 37 ms，语义引用 2,085 ms。容器和路由任务有重叠，阶段数值不可直接相加。候选扫描完成后的缓存等待 27 ms，连同写盘约 263 ms，不能解释主要耗时。

本轮对三个低风险假设做了冷查询验证，结果均保持 112 处及相同位置哈希，但没有稳定速度收益，因此未保留产品实现变更：跳过新文件的语义表面比较（旧版 9,016/9,578 ms；试验版 9,040/9,120 ms）；直接使用已解析成员访问事实筛选候选（单轮 9,103 ms，语义阶段 2,344 ms）；候选解析 worker 从 4 增至 6（对比 8,992 → 9,293 ms，候选阶段 4,482 → 4,679 ms）。这些数据表明当前机器上的瓶颈不是单一序列化、文本匹配或 worker 数量。

后续应针对候选准备和语义解析做更细的 CPU/等待分解，再修改算法；保持完整位置哈希、首次冷查询和取消/编辑失效行为作为接受条件。当前首次立即查询仍约 9 秒，未达到满意水平，Goal 继续。

## 后续分段采样

对同一冷查询再做正式 bundle 采样（8,871 ms，112 处及上述哈希不变）：`indexComposerSources` 处理 2,289 个项目文件，目录枚举 273 ms，预取等待合计 608 ms，逐文件应用合计 3,286 ms，缓存提交约 253 ms。另一轮更细的采样中，逐文件应用合计 3,425 ms；其中 `onSource` 1,691 ms，语义工作区更新 974 ms，快照创建 321 ms。计时埋点均已撤回，未加入产品运行路径。

未压缩 bundle 的 CPU profile 显示四个候选解析 worker 在该请求期间大部分样本为空闲，主线程出现 worker 消息反序列化、语义工作区更新和成员解析热点。将 PHPDoc 查找改为范围二分搜索的一次 A/B 测试为 9,248 → 9,232 ms，未达到稳定收益；预先跳过不含目标名字的 worker 任务，两组交叉测量中新版 8,938/9,178 ms、原版 9,055/9,065 ms，也处于波动范围。两项试验均已撤回。

下一阶段重点是减少短名字（例如 `get`）冷查询需要准备的声明文件数量，并在只读项目、包含继承与跨文件接收者类型的语料上核对完整位置集合。单纯增加 worker 或减少缓存写入，按本轮分段数据不足以解决首次约 9 秒的等待。

对同一 `get` 查询加临时声明访问计数后，语义引用阶段进行了 14,296 次 `fileAndDeclaration` 查找，但实际只触及 1,203 个延迟声明文件中的 24 个；首次查询 8,968 ms，112 处及位置哈希不变。埋点已撤回。这支持把延迟声明文件先保留为已准备的事实，按查询实际访问的类型再应用到工作区；实现前必须保证找不到类型时仍能保守回退，且跨文件继承、非 PSR-4 声明、开放编辑缓冲区及缓存恢复都不漏引用。现阶段不能仅凭 24/1,203 的单一语料数据跳过其余声明。

## 浅层声明与查询内缓存试验

实现过一版浅层声明注册：候选扫描时只登记解析器提供的原始声明，实际查到类型时再补齐 PHPDoc 与成员事实；缓存恢复保守地重新解析声明。Winstar `get` 首次查询的候选阶段由基线 4,792 ms 降到 4,295 ms，完整位置集合不变，但事件相关性检查会逐个访问已注册服务类并触发延迟补齐，事件阶段从约 35 ms 升到 1,633 ms，总耗时从 9,235 ms 升到 10,727 ms。加入只排除已证明无继承、接口或 trait 关系的预筛后，事件阶段降到约 0.3 秒；交叉测量仍出现新版 9,460 ms、基线 8,834 ms。该方案未表现出稳定总收益，已撤回。

另试过仅在一次 References 计算中缓存 `fileAndDeclaration` 查找，并在相关文件事实更新时失效；语义阶段约 2,156 ms，对照约 2,189 ms，处于测量波动范围，亦已撤回。两条试验均保持 112 处及相同位置 SHA-256；聚焦的 stdio 测试通过。它们表明延后声明工作和局部查找缓存没有消除关键路径，下一步应评估查询前可复用、有限时且可取消的项目准备，以及点击发生在准备过程中时的实际等待时间。不能把后台提前消耗的 CPU 时间表述为计算量减少。

## 项目预索引和重载成本

Winstar 2,289 个项目 PHP 文件，用现有 `indexComposerSources` 和完整语义更新做一次项目范围预索引，耗时 15,850 ms（不含完整扩展的 Doctrine/Symfony 分析）。把语言服务器直接切到现有 `experimental` 后立即发 References，查询仍为 9,575 ms、112 处；后台索引与按需候选扫描同时运行，未形成可复用的单一路径。未经任务合并与取消设计，不能默认开启完整后台索引，否则可能重新出现长时间“Indexing PHP symbols”。

相同缓存目录连续启动两次 on-demand 语言服务器：第一次 References 9,457 ms，第二次 7,445 ms，位置哈希相同。第二次候选扫描已恢复 1,655 个缓存候选，但仍花 2,947 ms，之后 Symfony 容器约 0.88 秒、语义查找约 2.22 秒。当前持久化的完整 References 结果只对没有语义/路由 Provider 的模式启用；在实际 Symfony 配置下，即使等待持久化任务，重载也不能直接复用完整查询结果。下一阶段若扩展持久化范围，必须先建立 Provider 输入和版本的完整证据校验，不能直接放宽开关。

Provider 输入审查确认 Symfony 服务分析读取项目配置 YAML/XML/PHP、编译容器 XML、Composer 元数据和依赖包配置资源。现有引用输入快照此前只发现目录中的 PHP 文件，无法证明新配置文件未出现。本轮扩展快照的可选文件扩展名选择，并测试 YAML/XML 的新增、修改及选择集变化会改变指纹；默认仍只选 PHP。Winstar `config/` 的 41 个匹配文件做一次完整快照约 37 ms。这个基础设施尚未使带 Symfony Provider 的结果缓存可用：仍需完整记录 Provider 命令/构建身份、所有实际与潜在配置目录、环境选择及其外部依赖，并验证结果缓存恢复时这些证据未变化。

把基准驱动的索引模式切为现有 `experimental` 并在 `initialized` 后等待 20 秒，Winstar 的首次点击仍需 15,407 ms；日志显示查询又启动了 2,289 文件候选扫描（11,575 ms），与尚未完成的完整索引争用资源。`discoverComposerRoots` 在此工作区只发现一个根，不能将延迟归咎于多项目发现。独立的项目 PHP 完整语义索引（不含完整扩展中的 Doctrine/Symfony 分析）为 15,850 ms，因此当前完整后台索引不能直接作为首次 References 加速方案。基准驱动现允许最多 30 秒的可选初始等待，便于把启动准备与点击延迟分开记录。

## 跳过非精确 token 声明的下界试验

基准驱动可用 `PHP_COMPANION_BENCHMARK_REFERENCE_LOCATIONS_PATH` 输出完整 LSP 位置数组，供两版逐项比较。临时试验完全不把 1,203 个只有 `get` 名字片段、没有精确 `get` token 的文件声明加入语义工作区；正式 bundle、空缓存、相同 Symfony Provider 下，首次 References 从基线 9,327 ms 降至 8,057 ms，但 112 处中漏掉 46 处，没有新增误报。漏项集中在依赖其他文件类/继承信息的控制器调用。试验代码已撤回。即使能零成本按需补齐全部必要声明，这一组样本的候选阶段可回收上界也约 1.3 秒，单独做声明延迟加载不足以把首次查询降到满意水平；精度优先，不能直接跳过这些文件。

## 扫描让出频率的验证

将候选索引主线程的让出间隔从每 10 个文件临时改为每 100 个文件，在同一次基线先行的空缓存 A/B 中，基线首次 References 为 8,874 ms、候选为 10,114 ms；候选扫描分别为 4,583 / 5,142 ms。两版都是 112 处，位置哈希相同。该改动已撤回，不能以减少事件循环调度次数代替结构性优化；更低让出频率还会损害取消请求的响应。下一步应把“项目候选准备、Provider 所需项目类型、语义引用查找”设计为可共享的工作单元，避免首次点击在同一批文件上重复准备事实；先以一处短名字查询建立结果集合和取消/编辑失效门槛，再扩展语料。

## 单次查询内的成员组合复用

正式 bundle 的 CPU profile 显示语义查找反复进入 `members()` 组合同一类型的继承及成员事实。现仅在一次同步 References 计算期间复用相同类型、访问作用域、可见性和模板参数的顶层成员列表；查询结束即清空，项目编辑或 Provider 更新不会跨查询复用旧结果。Winstar 同一 `get` 样本的两次空缓存 A/B 中，先跑旧版时语义阶段为 2,246 / 1,875 ms（旧/新），反向顺序为 2,308 / 2,091 ms；完整查询分别为 9,060 / 8,970 ms 和 9,528 / 9,141 ms。两组均为 112 处且位置哈希不变。收益集中于语义阶段，完整查询仍约 9 秒，不能据此称首次等待已解决。Semantic 291 项、聚焦 LSP 4 项、ESLint 和构建通过；尚未完成真实 WSL 编辑器操作验收。

## 双场景短循环

新增 `scripts/benchmark-reference-suite.mjs`，一次检查 Winstar 的短名字方法 `get` 和 Symfony 服务类 `AdminSecuritySubscriber`。每个样本独立空缓存，固定 Symfony Provider，并核对完整位置 SHA-256；可选传入旧 bundle 做结果与耗时 A/B。当前正式 bundle 单次运行分别为 9,023 ms / 112 处和 5,246 ms / 2 处。类查询的候选、容器、事件阶段约为 2.6 / 0.85 / 0.75 秒，语义阶段仅数毫秒；它与短名字方法的约 2 秒语义查找是不同瓶颈。两类工作负载必须分别通过，不能只优化一种。

把扫描并发预取从 128 临时降到 32 后，`get` 查询仍为 112 处且哈希一致，但候选阶段升到 5,929 ms、完整查询 9,994 ms；改动已撤回。后续不再单独降低预取并发，应优先让候选索引和 Provider 输入在首次查询前或查询间复用，并保证查询过程中没有第二个竞争性全项目扫描。

## Symfony 模式的跨进程结果复用

方法引用现在可以在候选扫描及 Symfony Provider 重新计算后，使用持久化的完整结果跳过昂贵的语义引用遍历。写入时记录外部语义事实及框架引用位置的指纹，恢复时要求指纹、引擎身份、Composer 输入、已加载源码与完整文件快照一致；不满足条件便正常重新计算。类查询的语义遍历仅需数毫秒，因此不做这种需要整项目快照的恢复。跨进程测试验证同输入命中，以及新增公开 Symfony 服务配置后拒绝旧结果并重算。

Winstar 的 `get` 样本同一缓存目录连续启动：首次 9,283 ms，第二次 6,553 ms，都是 112 处且位置哈希不变；第二次仍需候选恢复 2,845 ms 和容器/路由约 0.85 秒，快照验证抵消了部分语义遍历收益。新代码的独立空缓存双场景测量为 `get` 9,025 ms / 112 处、`AdminSecuritySubscriber` 5,190 ms / 2 处，位置哈希均不变。缓存尚未达到满意的首次等待时间，尤其不能代替真实 WSL 编辑器验收。

## 最近查询的空闲预热

持久化结果现在附带经过完整性校验的查询提示。重载后再次打开相同源码，若缓冲区内容与该提示对应的源码哈希一致，语言服务器在 1.5 秒空闲后静默准备最近的一个候选查询；完成后再准备 Symfony 容器和路由。References 与正在进行的同键候选扫描共用任务，取消或文件变化会使任务失效。背景准备不创建 VS Code 的索引进度通知；它提前消耗计算时间，并未减少首次空缓存的总工作量。

Winstar 的 `get` 样本在已有同版本缓存、打开文件后空闲 8 秒的独立进程中，后台候选恢复约 2.97 秒并完成框架准备，第一次点击 References 为 **1,636 ms**、112 处且位置哈希不变。点击发生在候选预热中途的 2.5 秒空闲场景只出现一次候选扫描，点击用时 5,337 ms；无匹配缓存的点击仍约 9 秒。聚焦 LSP 5 项、结果存储 3 项、构建及 ESLint 通过。以上均为 WSL 文件系统上的 LSP 基准，不是 VS Code Extension Host 实际交互验收；冷首次查询依旧不达标，Goal 继续。

同样保存服务类查询的安全提示，用于下次打开文件时预热候选和框架；其完整结果仍不做点击时的昂贵快照恢复。`AdminSecuritySubscriber` 的独立空缓存首次查询为 5,093 ms / 2 处，写入完成后重载并空闲 8 秒，首次点击为 **971 ms** / 2 处，位置哈希 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd` 不变。此数字依赖既有提示和足够的空闲准备时间，不能代表首次打开新项目时的速度。

## 光标符号的空闲预热

为首次打开、尚无历史查询提示的项目，扩展在活动 PHP 编辑器的光标位置稳定 300 ms 后把文件版本和位置发给语言服务器。语言服务器只对能够精确识别的一个项目符号生成查询提示，继续等待 1.5 秒空闲，再准备对应名字的候选文件与 Symfony 事实。光标移动、文件编辑或查询开始会使过期任务失效；背景任务不显示索引进度。文件打开与内容变化事件可能同时到达，服务器保留最新选择并避免较早的打开流程覆盖它。

Winstar 只读样本、独立空缓存、打开后空闲 8 秒、Symfony Provider 的双场景基准：`get` 首次点击 3,050 ms / 112 处，`AdminSecuritySubscriber` 972 ms / 2 处；位置 SHA-256 分别仍为 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2` 和 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`。另一次 `get` 为 2,417 ms；波动主要取决于点击时 Symfony 准备是否已结束。可用 `PHP_COMPANION_BENCHMARK_SELECTION_PREWARM=1 PHP_COMPANION_BENCHMARK_DOCUMENT_IDLE_MS=8000 node scripts/benchmark-reference-suite.mjs /var/www/php/8.5/winstar2024` 复测。这个优化把工作移到点击前，首次打开到可交互的总计算时间并未缩短；用户打开后立即点击仍走原有约 9 秒的精确查询路径。

最后一次构建后的复测为 `get` 2,673 ms / 112 处、服务类 946 ms / 2 处，SHA-256 均未变化。聚焦 LSP 5 项、TypeScript 类型检查、ESLint 和构建通过；尚未在真实 WSL VS Code Extension Host 验证光标空闲与点击行为。

## 点击发生在预热中途

活动编辑器选中符号的服务器端等待由 1.5 秒缩至 250 毫秒；客户端仍等待光标稳定 300 毫秒。基准驱动新增 `PHP_COMPANION_BENCHMARK_SELECTION_DELAY_MS=300`，让光标通知时序接近扩展的真实行为，并输出实际候选扫描次数。打开文件后 2.5 秒点击的两次独立空缓存测量中，`get` 为 6,404 / 6,948 ms（112 处），服务类为 4,466 / 4,262 ms（2 处）；每次只有一次候选扫描，位置哈希与原基线相同。先前 1.5 秒等待且立即发送光标通知的测量分别为 8,188 / 5,802 ms；两组通知时序不同，不能把差值当成严格 A/B 收益。打开后空闲 8 秒再点击为 `get` 2,361 ms、服务类 958 ms。

对立即点击另试过跳过无目标子串文件的 worker 准备，Winstar `get` 9,067 → 9,205 ms、服务类 4,986 → 5,913 ms，已撤回；直接遍历解析出的成员访问事实替代正则筛选，`get` 的语义阶段从 2,088 ms 升至 9,897 ms，亦已撤回。两项试验的完整引用位置哈希均未变化，说明当前热路径仍依赖现有 worker 预取与廉价正则预筛。250 毫秒预热提前消耗 CPU，并未解决打开后立即点击约 9 秒的等待；真实 WSL 编辑器的体感仍需验证。

最新正式 bundle 空缓存立即点击 `get` 为 9,455 ms，候选 4,717 ms、Symfony 路由 814 ms、语义 2,229 ms，112 处位置摘要不变。主线程与四个 worker 的 CPU profile 均显示实际工作，主线程有约 565 个 GC 样本，worker 各有约 3.5–3.7 千个 idle 样本；采样不能把这些数值直接换算为可回收的墙钟时间。将预读上限从 128 临时提高到 256，一组旧/新为 `get` 9,115/8,863 ms、类 5,100/5,326 ms，候选阶段几乎不变；跳过普通符号查询的命名参数摘要，一组旧/新为 `get` 8,862/9,396 ms、类 5,149/5,029 ms。这些差值无稳定双场景收益，两项均已撤回。继续优化立即点击需要改变候选事实准备或语义解析的工作量，而非单纯调大预读窗口或删掉摘要正则。

短循环脚本现在也输出候选扫描的文件与解析数量。原版独立空缓存 `get` 一次为 9,267 ms；2,289 个文件中解析 1,656 个，其中 1,203 个只登记声明，完整解析约 453 个；候选阶段 4,811 ms、语义阶段 1,964 ms，结果仍为相同的 112 处。试验把“完整解析”进一步限制为源码有直接 `->get`/`::get` 成员语法的文件，成对原版/试验版为 8,798/8,848 ms，候选阶段 4,545/4,604 ms，位置摘要不变，因此撤回。复核实现后确认，声明快照保留源码，查询另一符号时可按需加载方法体；先前关于缓存会直接漏掉另一符号的担忧不成立。后续优化应首先避免对大量候选文件做不必要的扫描或提供可证明安全的按需声明登记；仅把已匹配文件从完整解析改成声明解析，在此语料未缩短关键路径。

再做一次只解析含精确 `get`/`dispatch` 标识符文件的探索试验：解析数从 1,656 降至 453，候选阶段约 3,749 ms，首次完整请求约 7,668 ms，但结果只剩 66 处，位置摘要变为 `99eeb63176b80a8e54b2610e6e8ffe378c7c5ac5441eda56678b8c2d90b7c00e`。这证明被省略的声明文件对跨文件接收者类型是必需的；该试验立即撤回，不能以较低耗时替代完整的 112 处结果。下一步需要在按需声明登记前建立可验证的依赖闭包和保守回退。

进一步保存两组完整位置并逐项比较：丢失的 46 处只位于 6 个控制器，主要是继承得来的 `$this->request` 成员链。探索性地额外加载 Winstar 的 `AppController` 和 `AdminController` 后恢复到 111 处；再补 `NativeRecordController` 及中间的 `EmailRecordsController` 后恢复 112 处及原位置摘要，单次约 7,694 ms、候选 3,581 ms。该试验使用硬编码的项目类名，仅证明按继承依赖补声明具有潜力；不适合作为产品实现，已撤回。通用版本必须从已匹配源码提取并递归加载父类、接口和 trait，并对无法证明完整的接收者类型保守回退。

在上述只解析精确标识符、补齐四个基类且结果仍为 112 处的试验中，对成员查询增加临时计数，仍有 529 个同名语法位置无法解析为任何成员。因此不能把“存在未解析成员”作为自动触发完整扫描的条件；它在结果完整的语料上也会触发。临时计数、硬编码类型和精确筛选均已撤回并重建 bundle。安全的快速路径需要更强的依赖覆盖证明，或在候选文件集合之外建立一个可复用的声明目录。

继承闭包的粗略规模核查：Winstar 含完整 `get`/`dispatch` 标识符的 453 个 PHP 文件中，按源码行统计约有 1,043 条不同的 `use` 导入（其中 717 条 `App\\` 导入），但直接 `extends` 写法仅约 37 种。这些是文本计数，包含评论或别名歧义，不能当作语义解析后的准确依赖数；它提示只遍历直接父类可能较便宜，而盲目加载全部导入可能抵消收益。另将 Symfony 路由 Provider 从候选扫描之后移到之前并行执行，独立空缓存成对测试：`get` 9,238→9,030 ms，服务类 5,059→5,032 ms，位置摘要均不变；路由原本就和容器工作并行，净收益处于波动范围，试验已撤回。下一步聚焦声明目录和依赖闭包，不继续移动路由任务。

首次登记文件时，旧语义表面必然为空；语义工作区现在直接用新文件的声明与可调用项键建立失效集合，保留编辑已有文件时的完整表面比较。Winstar `get` 两轮独立空缓存成对测量为 9,077→8,800 ms、8,798→8,739 ms，112 处及完整位置摘要均不变；服务类一轮并行测试为 5,217→4,911 ms、2 处不变，但并行负载使该组不适合判断收益。Semantic 291 项、Language Server 232 项（另 1 项既有跳过）、改动文件 ESLint、构建通过。此优化只省去首次登记的重复序列化，不改变 1,656 个候选文件的解析规模；首次 `get` 仍约 9 秒，不能据此认为性能目标完成。

## 通用继承闭包试验（仅测试模式）

已实现不依赖 Winstar 类名的探索路径：从精确命中的候选文件提取类声明，逐层解析其直接父类、接口与 trait，并沿 Composer 映射按需加载声明。若项目命名空间下的依赖无法定位，或存在非 PSR-4 自动加载规则且依赖未解析，则退回原来的完整候选扫描。该路径须同时设置内部 `testMode` 与 `experimentalReferenceClosure` 初始化选项；扩展不向用户开放，正式 References 行为没有切换。短循环脚本可用 `PHP_COMPANION_BENCHMARK_REFERENCE_CLOSURE=1` 运行这个试验。

Winstar 独立空缓存 `get` 试验：精确候选解析 453 个文件，递归加载 80 个声明依赖；唯一未解析的 `PHPUnit\\Framework\\TestCase` 属于依赖包。首次查询约 7.6–8.0 秒，仍返回 112 处，位置摘要保持 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2`。无试验标志的正式路径仍解析约 1,656 个候选文件，一次空缓存测得 8,676 ms 和同一位置摘要。单次时间差只有约一秒，尚未达到满意的交互速度。

完成构建和全套测试后再次串行复测：默认路径 8,106 ms、实验路径 7,128 ms；两者各做一次空缓存扫描，分别解析 1,656/453 个文件，结果仍为相同的 112 处及完整位置摘要。Semantic 292 项、Language Server 233 项（另 1 项跳过）、改动文件 ESLint 与构建通过。该对测量支持约一秒量级的潜在收益，但仍只是单次样本。

为缩短下一轮验证，`benchmark-first-references.mjs` 新增 `PHP_COMPANION_BENCHMARK_COMPARE_REFERENCE_CLOSURE=1`：同一 bundle 串行运行默认和闭包试验，各用独立空缓存，自动核对引用数量与位置摘要。命令为 `PHP_COMPANION_BENCHMARK_COMPARE_REFERENCE_CLOSURE=1 PHP_COMPANION_EXPECTED_REFERENCES_SHA256=bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2 node scripts/benchmark-first-references.mjs /var/www/php/8.5/winstar2024 /var/www/php/8.5/winstar2024/src/Security/AdminPasswordChangeGuard.php get last`。首次运行 7,842/7,264 ms，差值 578 ms，仍为相同的 112 处。这个差值小于各轮环境波动，不作为上线收益承诺。

构造了一个非标准文件名的父类：`Consumer extends Base`，`Base` 的属性为 `Bag`，而 `Base` 声明在 `Legacy.php`。仅按精确 `get` 过滤时会漏掉 `Base` 并返回 0 处；新增回退后恢复为 1 处，完整位置摘要与正式扫描一致，并有 stdio 回归测试。这个例子证明回退必要，但不足以证明任意 Composer 项目的精确路径完整；尤其不能仅凭 PSR-4 解析成功就断言不存在其他动态或混合自动加载来源。正式启用前需要建立声明目录与可验证的覆盖条件，或采用更保守的回退策略，并对多种 Composer 布局及真实工作区做差分测试。

## 长名字源码预筛试验（仅测试模式）

对至少 8 个 ASCII 字符的查询名，实验性地先用本机 `rg` 对 Composer 项目自动加载路径执行不受 ignore 配置限制、包含隐藏文件和符号链接的固定子串搜索，再让原来的候选扫描只读取命中的 PHP 源码。项目文件仍逐一计数并检查大小预算；未命中的文件只有在修改时间与状态变更时间都早于预筛开始前 1 秒时才跳过读取。`rg` 缺失、超时、报错或输出超过预算时自动使用完整扫描。已存在且元数据未变化的候选缓存项保留。该路径须由内部 `testMode` 加 `experimentalRipgrepCandidates` 显式启用，正式扩展未启用，也不要求用户安装 `rg`。

Winstar 空缓存、Symfony Provider 的串行差分：`AdminSecuritySubscriber` 类声明 5,095→3,811 ms，完整 2 处位置摘要均为 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`；反向顺序再测，试验 3,764 ms、默认 5,001 ms。`shouldRedirect` 方法声明 4,721→3,572 ms，完整 1 处位置摘要一致。类名场景中 `rg` 用 82 ms 筛出 31 个文件，候选阶段从 2,614 降至 1,222 ms；方法场景筛出 33 个文件，候选阶段从 2,488 降至 1,232 ms。两场景解析文件数与默认路径一致，说明收益来自避免读取原本也不会加入语义工作区的源码。短名字 `get` 未启用该试验，仍需单独解决其约 8 秒首次等待。`PHP_COMPANION_BENCHMARK_COMPARE_REFERENCE_RG=1` 可在同一 bundle 上串行复测并自动核对位置。

这仍只是受控 WSL 基准。推广到正式路径前，需覆盖不同 Composer 自动加载布局、符号链接、文件变化窗口、缓存重载、`rg` 缺失以及真实 VS Code Extension Host；若无法证明预筛的文件集合完整，应继续走原扫描。即使这些条件通过，类名场景约 3.7 秒也尚未达到理想的首次交互速度，后续要进一步缩短 Symfony Provider 和语义准备时间。

已用清空 `PATH` 的独立进程验证 `rg` 缺失：`AdminSecuritySubscriber` 仍走原候选扫描，4,842 ms、2 处及相同位置摘要。项目索引包 36 项、Language Server 234 项（另 1 项跳过）、改动文件 ESLint 通过。预筛路径会少记录未读取文件的内容哈希，因此现有完整 References 结果的持久化证明不会生成；目前不能直接把这个局部加速默认打开，否则可能让重载后的已证实结果恢复退化。正式化需要为预筛集合建立同等严格的完整性证据或在后台补齐哈希，随后复测冷启动与重载两种场景。

## 短名字与语义阶段反证

临时把源码预筛门槛降至 3 个 ASCII 字符后，Winstar `get` 由 8,136 降到 7,418 ms；预筛跳过 633 个原本不会解析的文件，但语义候选仍是 1,656 个。反向串行测量却为试验 7,768 ms、默认 7,740 ms，候选阶段 4,495/4,441 ms，未复现稳定收益。门槛已恢复为 8，不能用长名字预筛声称解决短名字 `get`。

又试验在初次 PHP 解析时保存每个成员访问的语句起点，期望语义查找时避免重新建语法树。112 个 `get` 引用位置虽未变化，但语义阶段升至 5,667 ms，总耗时 11,565 ms；撤回试验并重建正式 bundle 后恢复为语义 1,806 ms、总耗时 7,831 ms，相同位置摘要。该方案触发了更昂贵的按需解析或查找路径，不能合并。CPU 采样仍显示候选更新、worker 通信、GC 与成员解析分担时间；仅移走语法树构建并不足以推断整体收益。

验证脚本增加 `PHP_COMPANION_BENCHMARK_REVERSE=1`，可在同一命令中先跑试验再跑基线，并在输出中记录运行顺序；不再需要分别手工运行两条命令。以类名预筛复测，试验先行为 3,711 ms、基线后行为 4,842 ms，2 处位置摘要相同。短名字冷查询仍是下一项重点。

## 预筛文件的持久化证据

预筛现在记录每个未读取 PHP 文件在扫描时的大小、修改时间与状态变更时间；写入 References 结果缓存前后再次逐一核对这些元数据，同时完整输入快照仍对 Composer 源码根中的全部 PHP 文件读取内容并计算哈希。证据集合要求每个项目源码恰好属于“已读取且哈希一致”或“预筛跳过且元数据未变”之一；任何缺项、重叠或扫描期间变化都放弃缓存写入。`referenceCandidateEvidenceMatches` 的这一扩展不改变普通完整扫描的校验要求。无匹配的源码仍可能在查询后的持久化阶段被完整快照读取，但这项后台工作不计入用户首次点击等待。

在 Winstar 无 Symfony Provider 的 `shouldRedirect` 样本中，试验性 `rg` 预筛首查 2,197 ms、1 处，后台日志确认 `[reference-cache] stored count=1`；重启语言服务器后返回相同位置，日志为 `restored count=1`，点击等待 2,380 ms。独立 `phpCompanion/testReferenceInputs` 审计返回 `captured=true`、`engineVerified=true`、2,537 个快照文件，候选已读文件 33 个。带 Symfony Provider 的 `AdminSecuritySubscriber` 首查 3,730 ms、2 处，也确认写入结果缓存；重启后的同一请求仍进行了候选扫描并重新写入，说明其框架事实恢复条件尚未满足，不能把“已写入”当作该场景“已快速恢复”。

证据改动后的默认（无实验标志）`get` 冷查询复测为 8,057 ms，候选 4,470 ms、语义 1,969 ms，仍是 112 处及原位置摘要；短名字瓶颈未改变。

## 有界预筛进入 Linux 正式路径

完整文件变化证据已通过单元、Winstar 输入审计与跨进程缓存恢复验证后，Linux 语言服务器默认对至少 8 个 ASCII 字符的普通符号查询尝试 `/usr/bin/rg`。使用绝对系统路径避免从工作区 `PATH` 执行未知程序；缺少该工具、退出异常、超过 1.5 秒或输出过大时自动回到原候选扫描。macOS/Windows 仍走原路径。基准驱动可用 `PHP_COMPANION_BENCHMARK_REFERENCE_RG=0` 强制原路径、`=1` 强制试验路径，以便差分；普通启动不传该内部初始化选项。

正式路径在 Winstar、Symfony Provider、`AdminSecuritySubscriber` 类声明空缓存首次查询测得 4,162 ms、2 处，完整位置摘要仍为 `c0d5d86b7e083c6f21354d508f2897712e0b7b6a8663efd6cf2066788ff221fd`，候选 1,337 ms，其中 `rg` 104 ms、筛出 31 个文件。已有 stdio 用例扩展为“磁盘文件不含类名、未保存缓冲区新增类引用”，仍返回磁盘与缓冲区中的完整引用。此优化尚未发布成新版 VSIX，也未在用户当前 WSL Alpha Profile 验证。它改善长名字，短名字 `get` 仍沿完整扫描，不满足最终目标。

正式路径改动后的完整 Language Server 测试为 235 项通过、1 项跳过；ESLint、TypeScript 构建通过。`get` 空缓存复测 7,781 ms、112 处，候选 4,450 ms、语义 1,850 ms，无 `rg` 预筛日志，位置摘要仍为 `bc8a76393e58d2675b906614cc4b375e6279aac344df5ea21d9cdffa02afc3b2`。

## 短名字冷查询的剩余关键路径

继续以独立空缓存和正式 bundle 测量 `get`：一次 8,042 ms，候选扫描 4,550 ms、语义引用 2,001 ms；重复采样的总时长约 7.8–8.1 秒，112 处位置摘要保持不变。临时阶段埋点显示，“打开文件后立即点击”的语义工作区初始化约 816 ms，磁盘结果恢复尝试约 347 ms，目标解析至候选扫描前约 180 ms，候选扫描 4,481 ms，语义引用 1,805 ms。阶段埋点已经撤回；这些数值是单机诊断样本，不应当相加作为稳定性能承诺。

把磁盘结果是否存在的检查移到引擎身份校验之前，首次仍为 8,096 ms；该试验已撤回。完全不配置候选缓存的两次首次查询为 7,011/7,147 ms，候选扫描 3,855/3,953 ms，结果仍为相同 112 处。缓存写入占约 0.6–0.9 秒，但即使牺牲这项重载能力，首次仍约 7 秒，不能作为主要修复。CPU profile 中候选 worker 有大量空闲样本；此前增加 worker 数量没有稳定收益。`src/` 内约 300 个 PHP 文件含直接 `->get` 或 `::get` 文本，与 1,656 个准备候选不同；语义阶段仍必须逐个证明接收者和成员身份，不能用文本位置代替引用结果。

下一轮实现应先针对有界候选准备与成员解析做共享、可取消的工作单元：查询、光标预热和后台准备复用同一批解析事实；编辑或 Composer 映射变化时失效；任何无法证明完整的声明或依赖仍走保守路径。验证只先跑 `get` 的一次空缓存完整位置哈希和阶段耗时，见到超过环境波动的收益后再做反向顺序 A/B、类名与提升属性样本、持久化重启、取消/编辑失效及 Extension Host。当前首查约 8 秒，性能 Goal 仍未完成。

又在仅测试模式把精确 token 的 `rg` 预筛与现有继承闭包组合：`rg` 61 ms 命中 453 个文件，候选阶段 3,303 ms、首次总计 6,804 ms，仍返回 112 处和相同位置摘要。这比单独的闭包试验仅进一步节省约数百毫秒，且闭包路径仍未证明任意 Composer 布局的完整性；试验已撤回，不进入正式扩展。
